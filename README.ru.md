[English](README.md) | **Русский**

[![CI](https://github.com/Zagorsky17/ServerSecurityGo/actions/workflows/ci.yml/badge.svg)](https://github.com/Zagorsky17/ServerSecurityGo/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/Zagorsky17/ServerSecurityGo)](https://github.com/Zagorsky17/ServerSecurityGo/releases)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Мониторинг и анализ процессов Linux-сервера (Ubuntu, Debian): поиск подозрительных процессов, признаков вредоносного ПО и несанкционированного вмешательства. Сканер читает `/proc`, оценивает каждый процесс по совокупности проверяемых признаков, объясняет оценку, хранит историю изменений и показывает всё в русскоязычной веб-панели.

**Приложение только наблюдает.** Оно не завершает процессы, не удаляет файлы и не блокирует соединения. Все решения принимает администратор.

- Один статический бинарник без зависимостей (только стандартная библиотека Go), интерфейс встроен в бинарник.
- По умолчанию панель доступна только на `127.0.0.1:8090`.
- Уровни риска: `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`, и к каждому уровню прилагается объяснение: какие правила сработали, с каким весом и на каких фактах.

## Установка с GitHub

На сервере под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | bash
```

Чтобы установить конкретную версию:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | SSG_VERSION=v0.1.0 bash
```

Что делает установщик:

1. Клонирует репозиторий в `/opt/serversecuritygo`. Репозиторий публичный, deploy key не нужен.
2. Если установлен Go 1.24+, собирает бинарник из исходников. Иначе скачивает готовый бинарник из [GitHub Releases](https://github.com/Zagorsky17/ServerSecurityGo/releases) и сверяет SHA256. Go на сервер ставить не обязательно.
3. Создаёт `/opt/serversecuritygo/.env` из `.env.example` с правами `600`.
4. Устанавливает `serversecuritygo.service`, включает и запускает службу, затем проверяет `/healthz`.

Если нет `git` или `curl`, установщик ставит их через `apt-get`. Других изменений в системе нет, чужие каталоги в `/opt` он не трогает.

Где что лежит:

| Что | Где |
|---|---|
| Код и бинарник | `/opt/serversecuritygo`, `/opt/serversecuritygo/bin/serversecuritygo` |
| Настройки | `/opt/serversecuritygo/.env` (права 600, в git не попадает) |
| Исключения (необязательно) | `/opt/serversecuritygo/allowlist.json` |
| История | `/var/lib/serversecuritygo` (права 700): `state.json`, `events.jsonl` |
| Резервные копии | `/var/backups/serversecuritygo` (права 700) |
| Логи | journald: `journalctl -u serversecuritygo` |
| systemd-юнит | `/etc/systemd/system/serversecuritygo.service` |

Ручная установка без скрипта:

```bash
git clone https://github.com/Zagorsky17/ServerSecurityGo /opt/serversecuritygo
cd /opt/serversecuritygo
make build          # или скачайте бинарник релиза в bin/serversecuritygo
install -m 600 .env.example .env
install -m 644 deploy/serversecuritygo.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now serversecuritygo
```

## Как открыть панель

Панель слушает только `127.0.0.1:8090`. С вашего компьютера её открывают через SSH-туннель:

```bash
ssh -L 8090:127.0.0.1:8090 root@<IP-сервера>
# затем в браузере: http://127.0.0.1:8090
```

Если вы подключаетесь по отдельному ключу, добавьте `-i ~/.ssh/<ключ> -o IdentitiesOnly=yes`.

## Возможности

**Сбор данных** идёт из `/proc` и связанных источников:

| Данные | Источник |
|---|---|
| PID, PPID, имя, состояние, потоки, время запуска, CPU (utime+stime) | `/proc/PID/stat` |
| UID/EUID/GID, RSS, PID в пространствах имён | `/proc/PID/status` |
| Командная строка (секреты маскируются) | `/proc/PID/cmdline` |
| Исполняемый файл, признак удаления, права, владелец | `/proc/PID/exe` (readlink + stat) |
| Рабочий каталог | `/proc/PID/cwd` |
| Открытые файлы и сокеты | `/proc/PID/fd/*` |
| TCP/UDP/Unix-сокеты по каждому сетевому пространству имён | `/proc/PID/net/{tcp,tcp6,udp,udp6,unix}` |
| Пространства имён и контейнеры (docker, containerd, kubernetes, podman, lxc) | `/proc/PID/ns/*`, `/proc/PID/cgroup` |
| Наличие `LD_PRELOAD`/`LD_AUDIT` (только имена, значения не хранятся) | `/proc/PID/environ` |
| Пользователи | `/etc/passwd` |
| Время загрузки, ОЗУ, ядро | `/proc/stat`, `/proc/meminfo`, `/proc/sys/kernel/osrelease` |

Системные проверки закрепления: `/etc/ld.so.preload`, cron (`/etc/crontab`, `/etc/cron.*`, `/var/spool/cron`), systemd-юниты в `/etc/systemd/system`, `/etc/rc.local`, `/etc/init.d`, `/etc/profile.d`, `.bashrc`, `update-motd.d`, `authorized_keys`.

**Веб-панель** (русский интерфейс, светлая и тёмная тема):

1. **Подозрительные** — процессы с признаками, отсортированные по риску. Для каждого показаны признаки, баллы, первое и последнее наблюдение и рекомендация.
2. **Все процессы** — поиск, сортировка по любому столбцу, фильтры по PID/PPID, пользователю, имени, пути и минимальному уровню риска.
3. **Дерево** — родительские и дочерние связи, сворачивание веток, подсветка найденного.
4. **Сеть** — сокеты с процессами-владельцами, фильтры по протоколу, состоянию и внешним адресам.
5. **История** — запуск, завершение, смена exe, cmdline или пользователя, рост и снижение риска, новые признаки, новые слушающие порты, системные находки.
6. **Система** — сведения о сервере, ограничения сканирования (права, контейнер) и проверки закрепления.
7. **Карточка процесса** — все собранные данные, объяснение оценки, факты по каждому признаку, рекомендации, цепочка предков, потомки, сокеты, открытые файлы и история процесса. Командную строку и JSON карточки можно скопировать, на карточку можно дать прямую ссылку (`#p=<ключ>`).

Панель обновляется автоматически, интервал от 5 до 60 секунд, можно выключить. Пока открыта карточка, автообновление приостанавливается.

## Как считается риск

Каждое правило выдаёт **признак**, то есть набор фактов: что прочитано и откуда, например `/proc/3101/exe → /dev/shm/.x/kworkerds`. Сам признак ничего не утверждает о вредоносности. У признака есть вес, категория и пометка «сильный», если он сам по себе редко бывает легитимным.

1. Сумма весов задаёт базовый уровень: от 1 балла LOW, от 15 MEDIUM, от 35 HIGH, от 60 CRITICAL.
2. Уровень ограничивается **числом независимых категорий** (расположение, целостность файла, маскировка, цепочка запуска, сеть, командная строка, поведение, окружение, привилегии, закрепление):
   - одна категория и ни одного сильного признака — не выше **LOW**. Поэтому только имя, только путь или только высокая нагрузка не дают больше LOW;
   - одна категория с сильным признаком — не выше **MEDIUM**;
   - две категории и меньше двух сильных признаков — не выше **HIGH**;
   - **CRITICAL** возможен только при трёх и более категориях или при двух сильных признаках.
3. Справочные признаки (процесс в контейнере, слушает порт, недостаточно прав) показываются, но на оценку не влияют.
4. Allowlist подавляет признаки известных легитимных процессов. Подавленный признак не скрывается, а показывается зачёркнутым и упоминается в объяснении.
5. Известные легитимные случаи учтены отдельно: бинарник в `/usr`, удалённый после `apt upgrade`, получает 4 балла вместо 20; `runc` через memfd ослаблен; unix-сокет журнала на stdout служб systemd не считается reverse shell; `node`, `java` и `python` как родители оболочки дают слабый признак.

Пример объяснения из карточки:

> Итог CRITICAL: 102 балл(ов), признаков — 4, категорий — 2 (командная строка, сеть), сильных — 2. Сработали: «Ввод/вывод оболочки или интерпретатора подключён к сетевому сокету» +40 (сильный); «Командная строка содержит конструкцию reverse shell» +35 (сильный); … Это оценка по косвенным признакам, а не доказательство компрометации.

## Примеры обнаруживаемых аномалий

Все примеры есть в демо-данных (`serversecuritygo demo`) и в автотестах.

| Сценарий | Сработавшие признаки | Уровень |
|---|---|---|
| Майнер в `/dev/shm/.x/`, `argv[0]="[kworker/u8:2]"`, соединение на порт 3333, длительная загрузка CPU | exe во временном каталоге, скрытый каталог, маскировка под поток ядра, порт пула, root из записываемого каталога, длительная загрузка CPU | CRITICAL |
| `nginx` → `sh -c 'bash -i >& /dev/tcp/…/4444 0>&1'` → `bash` с fd 0/1/2 на TCP-сокете | сетевой сервис запустил оболочку, конструкция reverse shell, stdin/stdout в сокете, внешнее соединение оболочки | CRITICAL |
| `/tmp/.ICE-unix/dbus-daemon (deleted)` с `LD_PRELOAD`, слушает `0.0.0.0:31337` | временный каталог, удалённый бинарник, имя системной службы вне системных путей, LD_PRELOAD, подозрительное прослушивание | CRITICAL |
| `cron` → `sh -c 'curl … \| sh'` | загрузка с немедленным выполнением, планировщик запускает загрузку | HIGH |
| Процесс из `memfd:` (безфайловый запуск) | запуск из памяти | MEDIUM |
| Компилятор с загрузкой CPU 95% | только длительная нагрузка | LOW |
| `sshd` после обновления пакета (`/usr/sbin/sshd (deleted)`) | системный бинарник заменён | LOW |
| `/etc/ld.so.preload` не пустой | глобальная подгрузка библиотек | HIGH (системная) |
| Задание cron `curl … \| sh` | подозрительная команда автозапуска | MEDIUM (системная) |
| Недавно изменён `authorized_keys` | недавнее изменение ключей SSH | LOW (системная) |

Полный список правил с идентификаторами для allowlist:
`exe_in_temp`, `exe_hidden_path`, `cwd_in_temp`, `exe_deleted`, `exe_memfd`, `exe_world_writable`, `exe_setuid_nonstd`, `exe_system_nonroot`, `kthread_masquerade`, `system_name_masquerade`, `name_mismatch`, `unusual_name`, `empty_cmdline`, `web_spawns_shell`, `scheduler_suspicious`, `stdio_socket`, `revshell_pattern`, `download_exec`, `miner_pattern`, `miner_name`, `pool_port`, `shell_network`, `suspicious_listen`, `cpu_sustained`, `mem_sustained`, `ld_preload`, `root_from_writable`. Системные проверки: `ld_so_preload`, `autostart_suspicious`, `autostart_temp`, `autostart_recent`, `ssh_key_command`, `ssh_keys_recent`.

## Ограничения обнаружения

Это эвристический инструмент для первичного анализа, а не антивирус и не EDR.

- **Руткиты уровня ядра** могут скрывать процессы, файлы и сокеты прямо в `/proc`. Сканер видит то, что показывает ядро. Пользовательские руткиты через `LD_PRELOAD` и `/etc/ld.so.preload` на сам сканер не действуют (статический бинарник Go без libc), но могут исказить вывод `ps`, `ls` и прочих утилит.
- **Снимки, а не события.** Сканирование идёт раз в `SSG_SCAN_INTERVAL` (по умолчанию 30 с), поэтому процессы, прожившие меньше интервала, могут не попасть в историю. Для полного аудита запусков нужны auditd или eBPF.
- **Нет анализа содержимого файлов:** ни сигнатур, ни хешей, ни репутации IP-адресов. Совпадения в командной строке (`stratum+tcp`, `/dev/tcp/`) ищутся по шаблонам, и их можно обойти переименованием или обфускацией.
- **Права.** Без root нельзя прочитать exe, cwd, fd и environ процессов других пользователей. То же бывает при `hidepid` на `/proc`, `kernel.yama.ptrace_scope=3` и строгих профилях AppArmor или SELinux. Сканер сообщает об этом в баннере и в карточке процесса.
- **Контейнеры.** Внутри контейнера сканер видит только его PID-пространство. Запускайте его на хосте. Пути exe и cwd процессов в контейнерах указаны внутри файловой системы контейнера, поэтому сравнение с системными путями хоста может ошибаться.
- **Ложные срабатывания** возможны у инструментов разработчика (`go run` из `/tmp`, сборки в CI), самописных служб в нестандартных каталогах, легального майнинга и установщиков вида `curl | sh`. Для них есть allowlist.
- **CPU%** считается по разнице `utime+stime` между сканированиями с `CLK_TCK=100`, как на x86_64 и arm64 в Ubuntu и Debian. При первом наблюдении процесса показывается среднее с момента запуска (отмечено `*`).
- **Сокеты** без найденного владельца (TIME_WAIT, сокеты ядра, нет прав) показываются со статусом «неизвестно». Если сокет открыт сразу у нескольких процессов (активация через systemd socket, master и worker nginx), в таблице «Сеть» указан первый найденный владелец, а в карточке каждого процесса сокет виден полностью.
- Отсутствие полей, которых нет в старых ядрах (например, `NSpid` до 4.1), допускается: такие сведения просто не показываются.

## Где проверено

| Окружение | Что проверено |
|---|---|
| Ubuntu 24.04.4 LTS, ядро 6.8.0, x86_64, 1 vCPU / 2 ГБ, Docker (тестовый VPS) | установка командой из README, работа службы под ограничениями systemd (у всех процессов прочитаны exe, fd, сокеты, ограничений нет), панель через SSH-туннель, `update.sh`, `rollback.sh`, `logs.sh`, сохранение истории между перезапусками, вход по паролю, отказ запуска на сетевом адресе без пароля или TLS, обнаружение безвредных имитаций (маскировка под kworker из `/tmp`, удалённый после запуска бинарник, bash с вводом из TCP-сокета) |
| GitHub Actions `ubuntu-latest` | все тесты, тест настоящего `/proc` от root, разовое сканирование системы раннера, shellcheck |
| macOS | тесты на поддельном `/proc`, демо-режим, интерфейс в Chrome |

На Debian приложение пока не запускалось. Оно использует только стандартные интерфейсы `/proc` и systemd, но проверка на Debian ещё впереди. Автоматический откат `update.sh` при неудачном запуске новой версии отдельно не воспроизводился. Ручной `rollback.sh` проверен.

Нагрузка на тестовом сервере (около 120 процессов): сканирование занимает около 60 мс, служба использует около 12 МБ памяти.

## Настройка

Все переменные с подробными комментариями перечислены в [`.env.example`](.env.example). Основные:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SSG_LISTEN_ADDR` | `127.0.0.1:8090` | адрес панели |
| `SSG_SCAN_INTERVAL` | `30s` | период сканирования (минимум `2s`) |
| `SSG_AUTH_PASSWORD_HASH` | — | хеш пароля (`serversecuritygo hash-password`) |
| `SSG_ALLOWED_HOSTS` | — | допустимые имена хоста для доступа из сети |
| `SSG_TLS_CERT` / `SSG_TLS_KEY` | — | собственный HTTPS |
| `SSG_TRUST_PROXY_TLS` | `false` | HTTPS завершается на reverse proxy |
| `SSG_CPU_THRESHOLD` / `SSG_CPU_SUSTAIN_SCANS` | `80` / `10` | порог и длительность высокой нагрузки |
| `SSG_HISTORY_RETENTION` | `168h` | хранение сведений о завершённых процессах |
| `SSG_ALLOWLIST_FILE` | `/opt/serversecuritygo/allowlist.json` | исключения |

После изменения `.env` выполните `systemctl restart serversecuritygo`.

**Allowlist.** Скопируйте [`allowlist.example.json`](allowlist.example.json) в `/opt/serversecuritygo/allowlist.json`. В правиле задаются `exe` и `name` (шаблоны `*` и `?`), `user` и список `rules` (идентификаторы признаков). Правило без условий игнорируется, чтобы случайно не подавить всё.

## Удалённый доступ

Рекомендуемый способ — SSH-туннель (см. выше): ничего не открывается наружу.

Если нужен прямой доступ, служба запустится только при выполнении всех условий:

1. Задан пароль:
   ```bash
   /opt/serversecuritygo/bin/serversecuritygo hash-password
   # вставьте выведенную строку SSG_AUTH_PASSWORD_HASH=... в .env
   ```
2. Задано имя, по которому открывается панель: `SSG_ALLOWED_HOSTS=mon.example.com`.
3. Включён HTTPS: либо `SSG_TLS_CERT` и `SSG_TLS_KEY`, либо reverse proxy с HTTPS и `SSG_TRUST_PROXY_TLS=true`. Во втором случае приложение лучше оставить на `127.0.0.1`.

Пример для nginx: приложение остаётся на `127.0.0.1:8090`, nginx отдаёт панель по HTTPS. В `.env` задайте `SSG_TRUST_PROXY_TLS=true` и пароль: при `SSG_TRUST_PROXY_TLS=true` служба без пароля не запустится, потому что сама не может проверить, открыл ли прокси её наружу.

```nginx
server {
    listen 443 ssl;
    server_name mon.example.com;
    ssl_certificate     /etc/letsencrypt/live/mon.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mon.example.com/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:8090;
        proxy_set_header Host 127.0.0.1;
    }
}
```

Пароль хранится только в виде хеша PBKDF2-SHA256 (600 000 итераций). После пяти неудачных попыток вход с этого адреса блокируется на 15 минут. Сессии живут в памяти, cookie помечены `HttpOnly`, `SameSite=Strict` и `Secure`.

Дополнительно можно ограничить доступ файрволом по IP, например `ufw allow from <ваш IP> to any port 443`.

## Обновление, откат, удаление, логи

```bash
/opt/serversecuritygo/scripts/update.sh            # до последнего релиза
/opt/serversecuritygo/scripts/update.sh v0.2.0     # до указанной версии
/opt/serversecuritygo/scripts/rollback.sh          # вернуть версию до последнего обновления
/opt/serversecuritygo/scripts/logs.sh              # журнал (последние 100 строк и слежение)
/opt/serversecuritygo/scripts/logs.sh -p warning --since today
/opt/serversecuritygo/scripts/uninstall.sh         # удалить службу, файлы и историю оставить
/opt/serversecuritygo/scripts/uninstall.sh --purge # удалить также /opt/serversecuritygo и историю
```

Как обновление защищено от сбоев:

- перед обновлением история, `.env` и `allowlist.json` архивируются в `/var/backups/serversecuritygo`, хранятся 5 последних архивов;
- новый бинарник проверяется (`version`), старый сохраняется как `bin/serversecuritygo.prev`;
- после перезапуска проверяется `/healthz`; если служба не поднялась, предыдущая версия возвращается автоматически.

Резервные копии не удаляются даже при `--purge`.

Состояние службы: `systemctl status serversecuritygo`.

## Консольный режим и демо

Разовое сканирование, не затрагивающее историю службы:

```bash
/opt/serversecuritygo/bin/serversecuritygo scan --env-file /opt/serversecuritygo/.env
/opt/serversecuritygo/bin/serversecuritygo scan --min-risk MEDIUM --sample 2s      # точный CPU по двум замерам
/opt/serversecuritygo/bin/serversecuritygo scan --format json --min-risk INFO > scan.json
```

Демонстрационный режим на вымышленных данных работает на любой ОС, в том числе на macOS:

```bash
go run ./cmd/serversecuritygo demo      # http://127.0.0.1:8090
```

## Сборка и тесты

Нужен Go 1.24 или новее; внешних модулей нет.

```bash
make build        # bin/serversecuritygo для текущей ОС
make build-linux  # dist/serversecuritygo-linux-{amd64,arm64} + SHA256SUMS
make test         # go test -race ./...
make vet          # gofmt + go vet
```

Тесты используют поддельное дерево `/proc` (`internal/fakeproc`), поэтому проходят на любой ОС. На Linux дополнительно выполняется `TestRealProc`: чтение настоящего `/proc`. GitHub Actions на каждый push и PR запускает тесты на Ubuntu, тест `/proc` от root, разовое сканирование реальной системы раннера, shellcheck скриптов и кросс-сборку. По тегу `v*` собирается релиз.

## Безопасность

- Только чтение: в коде нет kill, удаления файлов или изменения сетевых правил.
- Панель по умолчанию слушает только `127.0.0.1`. Сетевой адрес без пароля, `SSG_ALLOWED_HOSTS` и HTTPS не запустится.
- Проверка заголовка `Host` защищает от DNS rebinding, CSRF-токен защищает все POST-запросы, CSP запрещает inline-скрипты. Имена и командные строки процессов выводятся только как текст, поэтому злоумышленник не может внедрить HTML через имя своего процесса.
- Секреты в командных строках (`--password=…`, `-pПАРОЛЬ` у mysql, `user:pass@` в URL, `*_TOKEN=…`, ключи AWS и GitHub, JWT, токены Telegram) маскируются **до** анализа, сохранения и вывода. Значения переменных окружения не читаются в историю вообще. В журнал не пишутся пароли, cookie и командные строки.
- Служба работает от root, потому что без этого нельзя увидеть процессы других пользователей, но с урезанными возможностями: `CAP_SYS_PTRACE` и `CAP_DAC_READ_SEARCH`. Файловая система для службы только на чтение, кроме `/var/lib/serversecuritygo`; включены `NoNewPrivileges`, фильтр системных вызовов, лимиты `MemoryMax=256M` и `CPUQuota=50%`.
