Мониторинг и анализ процессов Linux-сервера (Ubuntu, Debian): поиск подозрительных процессов, признаков вредоносного ПО и несанкционированного вмешательства. Сканер читает `/proc`, оценивает каждый процесс по совокупности проверяемых признаков, объясняет оценку, хранит историю изменений и показывает всё в веб-панели и терминальном интерфейсе. Интерфейс доступен на русском и английском (см. [Язык](#язык)).

**Приложение только наблюдает.** Оно не завершает процессы, не удаляет файлы и не блокирует соединения. Все решения принимает администратор.

- Терминальный интерфейс в стиле lazygit: на сервере достаточно набрать `serversecuritygo`. Веб-панель через SSH-туннель — дополнительная возможность.
- Один статический бинарник без зависимостей (только стандартная библиотека Go), оба интерфейса встроены в бинарник.
- По умолчанию панель доступна только на `127.0.0.1:8090`.
- Уровни риска: `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`, и к каждому уровню прилагается объяснение: какие правила сработали, с каким весом и на каких фактах.

## Установка с GitHub

На сервере под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | bash
```

Чтобы установить конкретную версию:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | SSG_VERSION=v0.1.0 bash
```

Что делает установщик:

1. Клонирует репозиторий в `/opt/serversecuritygo`. Репозиторий публичный, deploy key не нужен.
2. Если установлен Go 1.24+, собирает бинарник из исходников. Иначе скачивает готовый бинарник из [GitHub Releases](https://github.com/Zagorsky17/ServerSecurityGo/releases) и сверяет SHA256. Go на сервер ставить не обязательно.
3. Создаёт `/opt/serversecuritygo/.env` из `.env.example` с правами `600`.
4. Устанавливает `serversecuritygo.service`, включает и запускает службу, затем проверяет `/healthz`.
5. Создаёт ссылку `/usr/local/bin/serversecuritygo`, чтобы интерфейс открывался одной командой.

Если нет `git` или `curl`, установщик ставит их через `apt-get`. Других изменений в системе нет, чужие каталоги в `/opt` он не трогает.

Где что лежит:

| Что | Где |
|---|---|
| Код и бинарник | `/opt/serversecuritygo`, `/opt/serversecuritygo/bin/serversecuritygo` |
| Настройки | `/opt/serversecuritygo/.env` (права 600, в git не попадает) |
| Исключения (необязательно) | `/opt/serversecuritygo/allowlist.json` |
| История | `/var/lib/serversecuritygo` (права 700): `state.json`, `events.jsonl` |
| Резервные копии | `/var/backups/serversecuritygo` (права 700) |
| Логи | journald: `journalctl -u serversecuritygo` |
| systemd-юнит | `/etc/systemd/system/serversecuritygo.service` |
| Команда запуска | `/usr/local/bin/serversecuritygo` (ссылка на бинарник) |
| Сокет для терминального интерфейса | `/run/serversecuritygo/api.sock` (права 600, только root; создаётся при запуске службы) |

Ручная установка без скрипта:

```bash
git clone https://github.com/Zagorsky17/ServerSecurityGo /opt/serversecuritygo
cd /opt/serversecuritygo
make build          # или скачайте бинарник релиза в bin/serversecuritygo
install -m 600 .env.example .env
install -m 644 deploy/serversecuritygo.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now serversecuritygo
```

| `r`, `p` | просканировать сейчас (на панели «Настройки» — проверить настройки сейчас), пауза автообновления |

| `+` | развернуть активную сторону на весь экран |
| `L` | язык интерфейса: русский / английский |

Работает и мышь: клик выбирает панель и строку, колесо прокручивает.

**Откуда берутся данные.** Если служба запущена, интерфейс подключается к ней через Unix-сокет `/run/serversecuritygo/api.sock`. Доступ к сокету есть только у root, поэтому пароль и туннель не нужны, а видна вся накопленная история. Если служба не запущена или установлена старая версия без сокета, интерфейс сканирует процессы сам, и тогда история хранится только на время сеанса. Источник указан в панели «Сводка».

```bash
serversecuritygo tui --local            # всегда сканировать самостоятельно
serversecuritygo tui --refresh 2s       # обновлять экран чаще
```

Чтобы видеть процессы всех пользователей, запускайте интерфейс от root (в режиме службы данные и так собирает служба).

Если копирование клавишей `y` не срабатывает: OSC 52 поддерживают iTerm2, kitty, WezTerm, Alacritty, Windows Terminal и современные xterm. В tmux нужна настройка `set -g set-clipboard on`.

## Веб-панель (по желанию)

Веб-панель повторяет те же данные в браузере. Она слушает только `127.0.0.1:8090`. С вашего компьютера её открывают через SSH-туннель:

```bash
ssh -L 8090:127.0.0.1:8090 root@<IP-сервера>
# затем в браузере: http://127.0.0.1:8090
```

Если вы подключаетесь по отдельному ключу, добавьте `-i ~/.ssh/<ключ> -o IdentitiesOnly=yes`.

Пока пароль не задан, служба пускает в панель только root: для каждого подключения к `127.0.0.1` она смотрит владельца сокета в `/proc/net/tcp`. Туннель под root работает, а другие пользователи сервера (например, взломанный `www-data`) получат ошибку 403. Если вы заходите по SSH под своим пользователем, добавьте его UID в `SSG_LOCAL_UIDS` (например, `0,1000`) или задайте пароль.

## Возможности

**Сбор данных** идёт из `/proc` и связанных источников:

| Данные | Источник |
|---|---|
| PID, PPID, имя, состояние, потоки, время запуска, CPU (utime+stime) | `/proc/PID/stat` |
| UID/EUID/GID, RSS, PID в пространствах имён | `/proc/PID/status` |
| Командная строка (секреты маскируются) | `/proc/PID/cmdline` |
| Исполняемый файл, признак удаления, права, владелец | `/proc/PID/exe` (readlink + stat) |
| Рабочий каталог | `/proc/PID/cwd` |
| Открытые файлы и сокеты | `/proc/PID/fd/*` |
| TCP/UDP/Unix-сокеты по каждому сетевому пространству имён | `/proc/PID/net/{tcp,tcp6,udp,udp6,unix}` |
| Пространства имён и контейнеры (docker, containerd, kubernetes, podman, lxc) | `/proc/PID/ns/*`, `/proc/PID/cgroup` |
| Наличие `LD_PRELOAD`/`LD_AUDIT` (только имена, значения не хранятся) | `/proc/PID/environ` |
| Пользователи | `/etc/passwd` |
| Адреса сервера (чтобы отличить публичные порты от частных) | `/proc/net/fib_trie`, `/proc/net/if_inet6` |
| Состояние и правила ufw | `/etc/ufw/ufw.conf`, `/etc/default/ufw`, `/etc/ufw/user.rules`, `/etc/ufw/user6.rules` |
| Настройки SSH | `/etc/ssh/sshd_config` с `Include` и `Match`, права `/etc/ssh/ssh_host_*_key` |
| Учётные записи (хеши паролей не показываются и не сохраняются — только тип алгоритма) | `/etc/passwd`, `/etc/shadow`, `/etc/group`, `/etc/login.defs`, `/etc/environment`, `.profile` и `.bashrc` пользователя root |
| Правила sudo | `/etc/sudoers` с `@include`/`@includedir`, алиасами и `Defaults` |
| Опубликованные порты Docker, имя и образ контейнера | аргументы `docker-proxy`, `<data-root>/containers/*/config.v2.json` (переменные окружения не попадают в структуры в памяти и нигде не показываются) |
| Время загрузки, ОЗУ, ядро | `/proc/stat`, `/proc/meminfo`, `/proc/sys/kernel/osrelease` |

Системные проверки закрепления: `/etc/ld.so.preload`, cron (`/etc/crontab`, `/etc/cron.*`, `/var/spool/cron`), systemd-юниты в `/etc/systemd/system`, `/etc/rc.local`, `/etc/init.d`, `/etc/profile.d`, `.bashrc`, `update-motd.d`, `authorized_keys`.

**Терминальный интерфейс** описан [выше](#терминальный-интерфейс). **Веб-панель** (русский и английский интерфейс, светлая и тёмная тема):

1. **Подозрительные** — процессы с признаками, отсортированные по риску. Для каждого показаны признаки, баллы, первое и последнее наблюдение и рекомендация.
2. **Все процессы** — поиск, сортировка по любому столбцу, фильтры по PID/PPID, пользователю, имени, пути и минимальному уровню риска.
3. **Дерево** — родительские и дочерние связи, сворачивание веток, подсветка найденного.
4. **Сеть** — сокеты с процессами-владельцами, фильтры по протоколу, состоянию и внешним адресам.
5. **Открытые порты** — что слушает сервер и откуда это доступно; см. [Открытые порты](#открытые-порты).
6. **Настройки безопасности** — аудит SSH, учётных записей и sudo; см. [Настройки безопасности](#настройки-безопасности).
7. **История** — запуск, завершение, смена exe, cmdline или пользователя, рост и снижение риска, новые признаки, новые слушающие порты, системные находки, изменения настроек безопасности.
8. **Система** — сведения о сервере, ограничения сканирования (права, контейнер), проверки закрепления и опасные открытые порты.
9. **Карточка процесса** — все собранные данные, объяснение оценки, факты по каждому признаку, рекомендации, цепочка предков, потомки, сокеты, открытые файлы и история процесса. Командную строку и JSON карточки можно скопировать, на карточку можно дать прямую ссылку (`#p=<ключ>`).

Панель обновляется автоматически, интервал от 5 до 60 секунд, можно выключить. Пока открыта карточка, автообновление приостанавливается.

### Открытые порты

Самая частая реальная причина взлома VPS — сервис, который случайно слушает `0.0.0.0`: Redis без пароля, MongoDB, Docker API, панель администратора. Вкладка **«Открытые порты»** (панель `5` в терминальном интерфейсе, `GET /api/exposure`, таблица в конце вывода `serversecuritygo scan`) показывает каждый слушающий TCP-сокет и привязанный UDP-сокет:

- **доступность**: *публичный* (любой адрес вне диапазонов ниже, включая `0.0.0.0` и `::` — все интерфейсы; рядом перечислены публичные адреса сервера), *частная сеть* (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`, link-local), *только локально* (`127.0.0.0/8`, `::1`) или *внутри контейнера* (сокет в своём сетевом пространстве имён: снаружи доступен только через опубликованный порт);
- процесс-владелец, пользователь и контейнер; для Docker — имя контейнера, образ и проброс портов;
- **узнанный сервис** из встроенной таблицы: Redis, Docker API, MongoDB, Elasticsearch/OpenSearch, etcd, kubelet, Jupyter, memcached, PostgreSQL, MySQL/MariaDB, RabbitMQ, CouchDB, SMB, RDP, VNC, Telnet, FTP, rpcbind, NFS, SNMP, экспортеры Prometheus. Сервис узнаётся по порту и имени процесса (или образу контейнера); совпадение только по номеру порта снижает уровень на ступень: на порту может работать другая программа;
- состояние **ufw** для порта: *открыт* (разрешающее правило для любых адресов), *закрыт* (ufw включён и не разрешает порт всем) или *в обход ufw*.

Уровень — опасность доступности сервиса, а не признак взлома: Redis из интернета — CRITICAL, PostgreSQL — HIGH, экспортер Prometheus — LOW. Если порт закрыт ufw, уровень снижается до LOW с пояснением, что сервис защищает только межсетевой экран. Каждый опасный публичный порт становится системной находкой с этим уровнем (она видна во вкладке «Система», в истории и в журнале) и признаком категории `exposure` в карточке процесса, который держит порт. Этот признак не «сильный»: сам по себе он поднимает легитимный процесс не выше LOW.

**Docker в обход ufw.** Docker добавляет свои правила iptables раньше правил ufw, поэтому `ufw deny 6379` не закрывает порт, опубликованный как `-p 6379:6379`. Если ufw включён, а порт контейнера опубликован на всех интерфейсах без разрешающего правила ufw, панель сообщает `fw_docker_bypass` (HIGH) и предлагает публиковать порт как `127.0.0.1:ПОРТ:ПОРТ` или ограничить его в цепочке `DOCKER-USER`. Опубликованные порты читаются из аргументов `docker-proxy` и из `config.v2.json` контейнеров, поэтому видны и при `userland-proxy: false`. Docker API не используется: его сокет даёт root, а наблюдателю он не нужен.

Чтобы не получать находку о намеренно открытом порте, добавьте правило allowlist для процесса с ID признака (например, `{"exe": "/usr/lib/postgresql/16/bin/postgres", "rules": ["exposed_database"]}`): признак процесса и системная находка будут показаны как подавленные и перестанут учитываться. Порты, опубликованные Docker без слушающего процесса (`userland-proxy: false`), так подавить нельзя.

### Настройки безопасности

Большинство взломов VPS происходит не через уязвимости нулевого дня, а через вход по паролю, лишний `NOPASSWD: ALL` или забытого пользователя. Вкладка **«Настройки безопасности»** (панель `6` в терминальном интерфейсе, `GET /api/audit`, команда `serversecuritygo audit`) проверяет конфигурацию — причины взлома, а не его следы.

Служба выполняет аудит сразу при запуске, затем каждые `SSG_AUDIT_INTERVAL` (по умолчанию час). Кнопка **«Проверить сейчас»** (`r` на панели в терминальном интерфейсе) запускает его немедленно — например, после исправления; пока идёт проверка, новая не запускается. На вкладке видно, когда была последняя проверка и сколько пройдено: «пройдено N из M» считает только проверки с результатом «в порядке», «опасно» или «требует внимания» (советы, «неприменимо» и «нет данных» не учитываются).

У каждой проверки есть результат (*в порядке*, *опасно*, *требует внимания*, *совет*, *неприменимо* — например, sshd не установлен, *нет данных* — нет прав на чтение), важность, факты с файлом и строкой (`/etc/ssh/sshd_config.d/50-cloud-init.conf:1 PasswordAuthentication yes`), рекомендация и часто готовая команда исправления. Приложение команду не выполняет: её запускаете вы. Перед изменением SSH проверьте вход по ключу в отдельной сессии.

| Группа | Проверки |
|---|---|
| SSH | `ssh_root_login`, `ssh_password_auth`, `ssh_empty_passwords`, `ssh_kbd_interactive` (пароль через PAM даже при `PasswordAuthentication no`), `ssh_max_auth_tries`, `ssh_x11_forwarding`, `ssh_tcp_forwarding` (`GatewayPorts`), `ssh_weak_crypto` (CBC, 3DES, RC4, MD5, SHA-1, DSA), `ssh_authkeys_file` (нестандартный файл ключей или `AuthorizedKeysCommand`), `ssh_host_keys_perms`, `ssh_config_perms`, советы `ssh_allow_users`, `ssh_banner_version`, `ssh_port` |
| Учётные записи | `acct_uid0_extra`, `acct_empty_password`, `acct_service_shell`, `acct_weak_hash` (MD5, DES), `acct_new`, `acct_priv_groups` (`sudo`, `admin`, `wheel`, `docker`, `lxd`, `disk`, `adm`, `shadow`), `acct_duplicate_ids`, `acct_passwd_perms`, `acct_home_perms`, `acct_root_path` |
| sudo | `sudo_nopasswd_all` (MEDIUM для облачных пользователей по умолчанию `ubuntu`, `debian`, `admin`…), `sudo_no_auth`, `sudo_gtfobins` (`vim`, `less`, `find`, `systemctl` и другие, из которых легко выйти в root-оболочку), `sudo_wildcard`, `sudo_writable_cmd`, `sudo_env_keep` (`LD_PRELOAD`, `PYTHONPATH`, `!env_reset`), `sudo_files_perms`, `sudo_changed` |

Настройки sshd разбираются так, как их читает сам sshd: `Include` раскрывается на месте, для ключа действует первое значение, блоки `Match` показываются отдельно («для пользователя X разрешён вход по паролю»), отсутствующие ключи берут значения OpenSSH по умолчанию. Разбор sudoers понимает `@include`/`@includedir` (файлы с точкой в имени пропускаются, как у sudo), алиасы, перенос строк и `Defaults`.

**Изменения.** Служба запоминает имена и UID пользователей, членов привилегированных групп и SHA-256 файлов sudoers в `/var/lib/serversecuritygo/audit-baseline.json` (права 600, без паролей и содержимого файлов). Новый пользователь, новый член привилегированной группы или правка sudoers переводят `acct_new`, `acct_priv_groups` или `sudo_changed` в «опасно» на сутки — следующий запуск не погасит тревогу молча. Если файл в каком-то запуске не прочитался, его часть базовой линии сохраняется, и потом ничего не окажется «новым». Каждое изменение результата («было в порядке — стало опасно», «исправлено») записывается во вкладку «История» и в журнал. Разовой команде `serversecuritygo audit` сравнивать не с чем, поэтому проверки изменений в ней «неприменимы».

### fail2ban

Вкладка **«fail2ban»** (панель в терминальном интерфейсе, `GET /api/fail2ban`) появляется, только если fail2ban установлен: есть `/etc/fail2ban` и `fail2ban-server` (или пакет dpkg) либо работает процесс `fail2ban-server`. Без fail2ban нет ни вкладки, ни панели, ни пустой заглушки; API отвечает `{"installed": false}`.

Что показывается за последние `SSG_AUTH_LOG_DAYS` дней (по умолчанию 14):

- состояние: запущен ли, версия, включённые jail с `maxretry`, `findtime`, `bantime` (и `bantime.increment`) и файлом, в котором jail включён; конфигурация читается так же, как её читает fail2ban: `jail.conf`, `jail.d/*.conf`, `jail.local`, `jail.d/*.local`, с `[DEFAULT]` и подстановкой `%(имя)s`;
- текущие баны: IP, jail, с какого времени, до какого (или навсегда), сколько раз этот адрес уже банили (рецидивисты) и готовая команда `fail2ban-client set <jail> unbanip <IP>` — приложение её не выполняет;
- интенсивность перебора паролей: попытки (строки `Found`) и баны по дням и по часам (графики в панели, мини-графики из блочных символов в терминале), итоги за сутки и за период, пиковый час;
- самые активные адреса и подсети /24 (/64 для IPv6) с несколькими атакующими адресами; адреса из `ignoreip`, которые продолжают перебор, помечены;
- последние события: баны, разбаны, восстановленные и продлённые баны, перезапуски fail2ban и jail.

Данные берутся только из файлов: `/var/log/fail2ban.log` (путь — из `logtarget` в `fail2ban.conf`/`fail2ban.local`) и его ротированных копий, в том числе `.gz`. `fail2ban-client` не вызывается. Ротированные файлы разбираются один раз, текущий дочитывается с места, где остановились, поэтому сканирование обходится в несколько `stat`. Текущие баны восстанавливаются по журналу (бан без последующего разбана с учётом `bantime`; перезапуск fail2ban снимает все баны до строк `Restore Ban`); точный список — `fail2ban-client status sshd`. IP-адреса — персональные данные: они хранятся только в памяти службы и не пишутся ни в `state.json`, ни в историю событий. Объём разбора ограничен (256 МБ на файл, 200 000 разных адресов на все файлы), поэтому журнал сервера под сильным перебором не исчерпает память службы.

Перебор на публичном сервере идёт постоянно, поэтому статистика справочная и на оценку процессов не влияет. Системные проверки:

| ID | Уровень | Когда |
|---|---|---|
| `fail2ban_not_running` | MEDIUM | fail2ban установлен, но `fail2ban-server` не запущен: защита от перебора выключена |
| `fail2ban_sshd_disabled` | LOW | SSH доступен из интернета, а ни один включённый jail его не защищает |
| `fail2ban_log_unavailable` | INFO | журнал пишется в journald/syslog (`logtarget = SYSTEMD-JOURNAL`) или файл не читается |

`fail2ban_sshd_disabled` можно подавить правилом allowlist для процесса `sshd`.

## Как считается риск

Каждое правило выдаёт **признак**, то есть набор фактов: что прочитано и откуда, например `/proc/3101/exe → /dev/shm/.x/kworkerds`. Сам признак ничего не утверждает о вредоносности. У признака есть вес, категория и пометка «сильный», если он сам по себе редко бывает легитимным.

1. Сумма весов задаёт базовый уровень: от 1 балла LOW, от 15 MEDIUM, от 35 HIGH, от 60 CRITICAL.
2. Уровень ограничивается **числом независимых категорий** (расположение, целостность файла, маскировка, цепочка запуска, сеть, командная строка, поведение, окружение, привилегии, закрепление):
   - одна категория и ни одного сильного признака — не выше **LOW**. Поэтому только имя, только путь или только высокая нагрузка не дают больше LOW;
   - одна категория с сильным признаком — не выше **MEDIUM**;
   - две категории и меньше двух сильных признаков — не выше **HIGH**;
   - **CRITICAL** возможен только при трёх и более категориях или при двух сильных признаках.
3. Справочные признаки (процесс в контейнере, слушает порт, недостаточно прав) показываются, но на оценку не влияют.
4. Allowlist подавляет признаки известных легитимных процессов. Подавленный признак не скрывается, а показывается зачёркнутым и упоминается в объяснении.
5. Известные легитимные случаи учтены отдельно: бинарник в `/usr`, удалённый после `apt upgrade`, получает 4 балла вместо 20; `runc` через memfd ослаблен; unix-сокет журнала на stdout служб systemd не считается reverse shell; `node`, `java` и `python` как родители оболочки дают слабый признак.

Пример объяснения из карточки:

> Итог CRITICAL: 102 балл(ов), признаков — 4, категорий — 2 (командная строка, сеть), сильных — 2. Сработали: «Ввод/вывод оболочки или интерпретатора подключён к сетевому сокету» +40 (сильный); «Командная строка содержит конструкцию reverse shell» +35 (сильный); … Это оценка по косвенным признакам, а не доказательство компрометации.

## Ограничения обнаружения

Это эвристический инструмент для первичного анализа, а не антивирус и не EDR.

- **Руткиты уровня ядра** могут скрывать процессы, файлы и сокеты прямо в `/proc`. Сканер видит то, что показывает ядро. Пользовательские руткиты через `LD_PRELOAD` и `/etc/ld.so.preload` на сам сканер не действуют (статический бинарник Go без libc), но могут исказить вывод `ps`, `ls` и прочих утилит.
- **Снимки, а не события.** Сканирование идёт раз в `SSG_SCAN_INTERVAL` (по умолчанию 30 с), поэтому процессы, прожившие меньше интервала, могут не попасть в историю. Для полного аудита запусков нужны auditd или eBPF.
- **Нет анализа содержимого файлов:** ни сигнатур, ни хешей, ни репутации IP-адресов. Совпадения в командной строке (`stratum+tcp`, `/dev/tcp/`) ищутся по шаблонам, и их можно обойти переименованием или обфускацией.
- **Права.** Без root нельзя прочитать exe, cwd, fd и environ процессов других пользователей. То же бывает при `hidepid` на `/proc`, `kernel.yama.ptrace_scope=3` и строгих профилях AppArmor или SELinux. Сканер сообщает об этом в баннере и в карточке процесса.
- **Контейнеры.** Внутри контейнера сканер видит только его PID-пространство. Запускайте его на хосте. Пути exe и cwd процессов в контейнерах указаны внутри файловой системы контейнера, поэтому сравнение с системными путями хоста может ошибаться.
- **Ложные срабатывания** возможны у инструментов разработчика (`go run` из `/tmp`, сборки в CI), самописных служб в нестандартных каталогах, легального майнинга и установщиков вида `curl | sh`. Для них есть allowlist.
- **CPU%** считается по разнице `utime+stime` между сканированиями с `CLK_TCK=100`, как на x86_64 и arm64 в Ubuntu и Debian. При первом наблюдении процесса показывается среднее с момента запуска (отмечено `*`).
- **Сокеты** без найденного владельца (TIME_WAIT, сокеты ядра, нет прав) показываются со статусом «неизвестно». Если сокет открыт сразу у нескольких процессов (активация через systemd socket, master и worker nginx), в таблице «Сеть» указан первый найденный владелец, а в карточке каждого процесса сокет виден полностью.
- **Открытые порты** оцениваются только по адресу, на котором слушает сокет, и по ufw. Сервис на собственном частном адресе сервера (например, `172.31.5.10` в AWS или GCP) показан как *частная сеть*, хотя при 1:1 NAT провайдера он может быть доступен из интернета по публичному IP — проверьте группы безопасности у провайдера. Правила, добавленные напрямую через `iptables`/`nftables`, firewalld и облачные межсетевые экраны не читаются.
- Отсутствие полей, которых нет в старых ядрах (например, `NSpid` до 4.1), допускается: такие сведения просто не показываются.

## Настройка

Все переменные с подробными комментариями перечислены в [`.env.example`](.env.example). Основные:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SSG_LISTEN_ADDR` | `127.0.0.1:8090` | адрес веб-панели |
| `SSG_SOCKET_PATH` | `/run/serversecuritygo/api.sock` | сокет для терминального интерфейса (`off` — выключить) |
| `SSG_SCAN_INTERVAL` | `30s` | период сканирования (минимум `2s`) |
| `SSG_AUTH_PASSWORD_HASH` | — | хеш пароля (`serversecuritygo hash-password`) |
| `SSG_ALLOWED_HOSTS` | — | допустимые имена хоста для доступа из сети |
| `SSG_TLS_CERT` / `SSG_TLS_KEY` | — | собственный HTTPS |
| `SSG_TRUST_PROXY_TLS` | `false` | HTTPS завершается на reverse proxy |
| `SSG_CPU_THRESHOLD` / `SSG_CPU_SUSTAIN_SCANS` | `80` / `10` | порог и длительность высокой нагрузки |
| `SSG_HISTORY_RETENTION` | `168h` | хранение сведений о завершённых процессах |
| `SSG_ALLOWLIST_FILE` | `/opt/serversecuritygo/allowlist.json` | исключения |
| `SSG_LANG` | — (авто) | язык по умолчанию: `ru` или `en` |
| `SSG_AUDIT_ENABLED` | `true` | аудит настроек безопасности в службе |
| `SSG_AUDIT_INTERVAL` | `1h` | как часто повторять аудит (минимум `1m`) |
| `SSG_AUTH_LOG_DAYS` | `14` | за сколько дней разбирать журнал fail2ban (1–365) |

После изменения `.env` выполните `systemctl restart serversecuritygo`.

**Allowlist.** Скопируйте [`allowlist.example.json`](allowlist.example.json) в `/opt/serversecuritygo/allowlist.json`. В правиле задаются `exe` и `name` (шаблоны `*` и `?`), `user` и список `rules` (идентификаторы признаков). Правило без условий игнорируется, чтобы случайно не подавить всё. Имя процесса (`comm`) процесс задаёт сам, поэтому правило без `exe` срабатывает, только если имя совпадает и с именем исполняемого файла: майнер, назвавшийся `node`, под правило `{"name": "node"}` не попадёт. Для программ на интерпретаторах (например, `gunicorn` на Python) указывайте `exe`. О правилах без `exe` служба предупреждает в журнале при запуске.

## Язык

Все тексты, которые видит пользователь, есть на русском и английском: веб-панель и страница входа, терминальный интерфейс, названия признаков, доказательства, объяснение оценки, рекомендации, события истории, предупреждения сканера, вывод `scan` и `--help`, журнал службы и сообщения об ошибках.

- **Веб-панель.** Кнопка **English / Русский** в шапке (и на странице входа) переключает язык сразу, выбор запоминается в браузере. Пока пользователь не выбрал язык, панель берёт `SSG_LANG`, а если она не задана — язык браузера (`Accept-Language`).
- **Терминальный интерфейс.** Язык переключает клавиша `L`. Начальный язык — `SSG_LANG` или локаль терминала (`LC_ALL`, `LC_MESSAGES`, `LANG`).
- **Командная строка и журнал службы.** `SSG_LANG`, иначе локаль. При пустой локали, `C` или `POSIX` (обычно так у служб systemd) вывод на русском; для английского журнала службы укажите `SSG_LANG=en` в `/opt/serversecuritygo/.env`.

Сканер хранит тексты сообщениями (ключ каталога и аргументы), а строку каждый клиент собирает на своём языке, поэтому два пользователя могут одновременно смотреть один сервер на разных языках. Переводы лежат в [`internal/i18n`](internal/i18n): в `catalog_*.go` русский и английский текст стоят рядом, а тесты проверяют, что у каждого ключа есть оба перевода с одинаковыми плейсхолдерами.

**JSON API.** Текстовые поля (`title`, `evidence`, `recommendation`, `explanation`, `recommendations`, `warnings`, `details` событий) — либо простая строка (факт из системы, например путь), либо объект-сообщение `{"key": "…", "args": […]}` (`{"sep": "…", "parts": […]}` для склеенного текста). Каталог одного языка отдаётся по `GET /i18n/ru.json` или `/i18n/en.json`. `scan --format json` выводит готовый текст на языке процесса, а не объекты-сообщения. Ошибки API приходят на языке из заголовка запроса `X-SSG-Lang`.

## Удалённый доступ

Рекомендуемый способ — SSH-туннель (см. выше): ничего не открывается наружу.

Если нужен прямой доступ, служба запустится только при выполнении всех условий:

1. Задан пароль:
   ```bash
   /opt/serversecuritygo/bin/serversecuritygo hash-password
   # вставьте выведенную строку SSG_AUTH_PASSWORD_HASH=... в .env
   ```
2. Задано имя, по которому открывается панель: `SSG_ALLOWED_HOSTS=mon.example.com`.
3. Включён HTTPS: либо `SSG_TLS_CERT` и `SSG_TLS_KEY`, либо reverse proxy с HTTPS и `SSG_TRUST_PROXY_TLS=true`. Во втором случае приложение лучше оставить на `127.0.0.1`.

Пример для nginx: приложение остаётся на `127.0.0.1:8090`, nginx отдаёт панель по HTTPS. В `.env` задайте `SSG_TRUST_PROXY_TLS=true` и пароль: при `SSG_TRUST_PROXY_TLS=true` служба без пароля не запустится, потому что сама не может проверить, открыл ли прокси её наружу.

```nginx
server {
    listen 443 ssl;
    server_name mon.example.com;
    ssl_certificate     /etc/letsencrypt/live/mon.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mon.example.com/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:8090;
        proxy_set_header Host 127.0.0.1;
        # Адрес клиента для ограничения попыток входа: без него все
        # клиенты выглядят как 127.0.0.1 и делят один счётчик.
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
```

Пароль хранится только в виде хеша PBKDF2-SHA256 (600 000 итераций). После пяти неудачных попыток вход с этого адреса (для IPv6 — с сети /64) блокируется на 15 минут. Попытка учитывается до проверки пароля, поэтому параллельные запросы лимит не обходят, а одновременно проверяется не больше двух паролей. За reverse proxy адрес клиента берётся из `X-Forwarded-For`, который выставляет прокси (см. пример выше). Сессии живут в памяти, cookie помечены `HttpOnly`, `SameSite=Strict` и `Secure`.

Дополнительно можно ограничить доступ файрволом по IP, например `ufw allow from <ваш IP> to any port 443`.

## Обновление, откат, удаление, логи

```bash
/opt/serversecuritygo/scripts/update.sh            # до последнего релиза
/opt/serversecuritygo/scripts/update.sh v0.2.0     # до указанной версии
/opt/serversecuritygo/scripts/rollback.sh          # вернуть версию до последнего обновления
/opt/serversecuritygo/scripts/logs.sh              # журнал (последние 100 строк и слежение)
/opt/serversecuritygo/scripts/logs.sh -p warning --since today
/opt/serversecuritygo/scripts/uninstall.sh         # удалить службу, файлы и историю оставить
/opt/serversecuritygo/scripts/uninstall.sh --purge # удалить также /opt/serversecuritygo и историю
/opt/serversecuritygo/scripts/uninstall.sh --full  # полная очистка (см. ниже)
```

Как обновление защищено от сбоев:

- перед обновлением история, `.env` и `allowlist.json` архивируются в `/var/backups/serversecuritygo`, хранятся 5 последних архивов;
- новый бинарник проверяется (`version`), старый сохраняется как `bin/serversecuritygo.prev`;
- после перезапуска проверяется `/healthz`; если служба не поднялась, предыдущая версия возвращается автоматически.
- после переключения исходников обновление продолжает скрипт уже новой версии, поэтому её новые шаги срабатывают сразу. Исключение — обновление с v0.1.x: там новый скрипт ещё не запускался, и ссылку `/usr/local/bin/serversecuritygo` нужно создать вручную (`ln -sfn /opt/serversecuritygo/bin/serversecuritygo /usr/local/bin/serversecuritygo`) или выполнить `update.sh` повторно.

Резервные копии не удаляются даже при `--purge`.

**Обновление до v0.3.0 (английский язык).** Запустите `update.sh` как обычно; миграция не нужна, накопленная история сохраняется. После обновления:

- веб-панель открывается на языке браузера, в шапке есть переключатель **English / Русский**; в терминальном интерфейсе язык переключает клавиша `L`;
- журнал службы остаётся на русском; для английского добавьте `SSG_LANG=en` в `/opt/serversecuritygo/.env` и выполните `systemctl restart serversecuritygo`;
- если ваши скрипты читают JSON API, учтите, что текстовые поля теперь могут быть объектами-сообщениями (см. [Язык](#язык)); `scan --format json` по-прежнему выводит готовый текст.

### Полное удаление

Удаляет приложение так, будто его на сервере никогда не было: служба и её следы в systemd, ссылка `/usr/local/bin/serversecuritygo`, `/opt/serversecuritygo`, история `/var/lib/serversecuritygo` и резервные копии `/var/backups/serversecuritygo`. Действие необратимо.

```bash
/opt/serversecuritygo/scripts/uninstall.sh --full -y
```

Если каталог `/opt/serversecuritygo` уже удалён или повреждён, ту же очистку выполняет одна команда без скриптов:

```bash
systemctl disable --now serversecuritygo 2>/dev/null; \
rm -rf /etc/systemd/system/serversecuritygo.service /etc/systemd/system/serversecuritygo.service.d; \
systemctl daemon-reload; systemctl reset-failed serversecuritygo 2>/dev/null; \
[ -L /usr/local/bin/serversecuritygo ] && rm -f /usr/local/bin/serversecuritygo; \
rm -rf /opt/serversecuritygo /var/lib/serversecuritygo /var/backups/serversecuritygo /run/serversecuritygo
```

Чего команда не трогает, и почему:

- **пакеты `git`, `curl`, `ca-certificates`.** Установщик ставит их, только если их не было, но они нужны и другим программам. Если вы уверены, что они не нужны: `apt-get remove git curl`;
- **записи в journald.** Удалить записи одной службы нельзя, не стерев журнал всей системы. Они исчезнут сами по мере ротации журнала.

Проверить, что следов не осталось:

```bash
systemctl status serversecuritygo        # Unit serversecuritygo.service could not be found.
ls -d /opt/serversecuritygo /var/lib/serversecuritygo /var/backups/serversecuritygo /usr/local/bin/serversecuritygo   # No such file or directory
```

Состояние службы: `systemctl status serversecuritygo`.

## Консольный режим и демо

Разовое сканирование, не затрагивающее историю службы:

```bash
/opt/serversecuritygo/bin/serversecuritygo scan --env-file /opt/serversecuritygo/.env
/opt/serversecuritygo/bin/serversecuritygo scan --min-risk MEDIUM --sample 2s      # точный CPU по двум замерам
/opt/serversecuritygo/bin/serversecuritygo scan --format json --min-risk INFO > scan.json
```

Разовая проверка настроек безопасности (SSH, учётные записи, sudo); `--all` показывает и пройденные проверки:

```bash
/opt/serversecuritygo/bin/serversecuritygo audit
/opt/serversecuritygo/bin/serversecuritygo audit --format json > audit.json
```

**Форматы отчёта.** `scan` и `audit` принимают `--format`:

| Формат | Для чего |
|---|---|
| `text` (по умолчанию) | терминал |
| `json` | скрипты и Ansible: стабильная схема с `schema_version`, `verdict`, `incomplete` |
| `html` | владелец сервера: один самодостаточный файл (встроенный CSS, без скриптов, светлая и тёмная тема) с итогом, сводкой, находками и рекомендациями |
| `md` | документация или тикет: таблицы Markdown, всё взятое из системы экранировано |

`--output ФАЙЛ` пишет отчёт в файл с правами 600 (в отчёте командные строки и пути) вместо вывода на экран. Файл заменяется атомарно; символическая ссылка отвергается, а в устройство вроде `/dev/null` запись идёт напрямую:

```bash
serversecuritygo audit --format html --output /root/audit.html
serversecuritygo scan --format md --output /root/scan.md
```

**Коды выхода** позволяют запускать проверки из cron, CI, Ansible или мониторинга:

| Код | Значение |
|---|---|
| `0` | нет находок уровня `--fail-on` и выше |
| `1` | есть находки уровня `--fail-on` и выше (по умолчанию `HIGH`) |
| `2` | ошибка: `/proc` не читается вовсе, сломана конфигурация, неверный флаг |
| `3` | таких находок нет, но проверка неполная: часть данных не прочитана (запустите от root) |

`--fail-on` принимает `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` или `none`. Находки важнее неполноты: код 1 возвращается, даже если часть данных не прочитана. `--fail-on none` делает код независимым от находок (остаются только 2 и 3). **Для существующих скриптов:** раньше `scan` всегда завершался с кодом 0, теперь при находках HIGH или CRITICAL — с кодом 1; где нужно прежнее поведение, добавьте `--fail-on none`. Для `scan` уровень — наивысший риск процесса или системной находки (`--min-risk` только фильтрует вывод), для `audit` — наивысшая важность проверки со статусом «опасно» или «требует внимания».

```bash
# ежедневно в 6:00: отчёт аудита в файл, письмо от cron, если что-то не так
0 6 * * * /opt/serversecuritygo/bin/serversecuritygo audit --fail-on HIGH --format md --output /root/audit.md || echo "настройки безопасности требуют внимания: /root/audit.md"
```

Демонстрационный режим на вымышленных данных работает на Linux и macOS:

```bash
go run ./cmd/serversecuritygo demo --tui   # в терминале
go run ./cmd/serversecuritygo demo         # в браузере: http://127.0.0.1:8090
```

## Сборка и тесты

Нужен Go 1.24 или новее; внешних модулей нет.

```bash
make build        # bin/serversecuritygo для текущей ОС
make build-linux  # dist/serversecuritygo-linux-{amd64,arm64} + SHA256SUMS
make test         # go test -race ./...
make vet          # gofmt + go vet
```

Тесты используют поддельное дерево `/proc` (`internal/fakeproc`), поэтому проходят на любой ОС. На Linux дополнительно выполняется `TestRealProc`: чтение настоящего `/proc`. GitHub Actions на каждый push и PR запускает тесты на Ubuntu, тест `/proc` от root, разовое сканирование реальной системы раннера, shellcheck скриптов и кросс-сборку. По тегу `v*` собирается релиз.

## Безопасность

- Только чтение: в коде нет kill, удаления файлов или изменения сетевых правил.
- Терминальный интерфейс получает данные через Unix-сокет с правами `600` в каталоге `700`. Права файла и есть авторизация, поэтому подключиться может только root. Управляющие символы из имён процессов и командных строк в терминал не выводятся, так что имя процесса не может выполнить ESC-последовательность в вашем терминале.
- Веб-панель по умолчанию слушает только `127.0.0.1`. Сетевой адрес без пароля, `SSG_ALLOWED_HOSTS` и HTTPS не запустится.
- Без пароля панель доступна только пользователям из `SSG_LOCAL_UIDS` (по умолчанию root): владелец каждого подключения к loopback определяется по `/proc/net/tcp`, остальные получают 403. Иначе любой локальный пользователь мог бы читать то, что служба собирает от root: пути, открытые файлы и сокеты чужих процессов, результаты проверок.
- Проверка заголовка `Host` защищает от DNS rebinding, CSRF-токен защищает все POST-запросы, CSP запрещает inline-скрипты. Имена и командные строки процессов выводятся только как текст, поэтому злоумышленник не может внедрить HTML через имя своего процесса.
- Секреты в командных строках (`--password=…`, `-pПАРОЛЬ` у mysql, `user:pass@` в URL, `*_TOKEN=…`, ключи AWS и GitHub, JWT, токены ботов) маскируются **до** анализа, сохранения и вывода. Значения переменных окружения не читаются в историю вообще. В журнал не пишутся пароли, cookie и командные строки.
- Служба работает от root, потому что без этого нельзя увидеть процессы других пользователей, но с урезанными возможностями: `CAP_SYS_PTRACE` и `CAP_DAC_READ_SEARCH`. Файловая система для службы только на чтение, кроме `/var/lib/serversecuritygo`; включены `NoNewPrivileges`, фильтр системных вызовов, лимиты `MemoryMax=256M` и `CPUQuota=50%`.
