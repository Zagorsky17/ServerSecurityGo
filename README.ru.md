# ServerSecurityGo

[English](README.md) | **Русский** | [简体中文](README.zh-CN.md)

[![Release](https://img.shields.io/github/v/release/Zagorsky17/ServerSecurityGo)](https://github.com/Zagorsky17/ServerSecurityGo/releases)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Мониторинг и анализ процессов Linux-сервера (Ubuntu, Debian): поиск подозрительных процессов, признаков вредоносного ПО и несанкционированного вмешательства. Сканер читает `/proc`, оценивает каждый процесс по совокупности проверяемых признаков, объясняет оценку, хранит историю изменений и показывает всё в веб-панели и терминальном интерфейсе. Интерфейс доступен на русском и английском (см. [Язык](#язык)).

**Приложение только наблюдает.** Оно не завершает процессы, не удаляет файлы и не блокирует соединения. Все решения принимает администратор.

- Терминальный интерфейс в стиле lazygit: на сервере достаточно набрать `serversecuritygo`. Веб-панель через SSH-туннель — дополнительная возможность.
- Один статический бинарник без зависимостей (только стандартная библиотека Go), оба интерфейса встроены в бинарник.
- По умолчанию панель доступна только на `127.0.0.1:8090`.
- Уровни риска: `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`, и к каждому уровню прилагается объяснение: какие правила сработали, с каким весом и на каких фактах.

## Установка с GitHub

На сервере под root:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | bash
```

Чтобы установить конкретную версию:

```bash
curl -fsSL https://raw.githubusercontent.com/Zagorsky17/ServerSecurityGo/main/scripts/install.sh | SSG_VERSION=v0.1.0 bash
```

Что делает установщик:

1. Клонирует репозиторий в `/opt/serversecuritygo`. Репозиторий публичный, deploy key не нужен.
2. Если установлен Go 1.27.4+, собирает бинарник из исходников. Иначе скачивает готовый бинарник из [GitHub Releases](https://github.com/Zagorsky17/ServerSecurityGo/releases) и сверяет SHA256. Go на сервер ставить не обязательно.
3. Создаёт `/opt/serversecuritygo/.env` из `.env.example` с правами `600`.
4. Устанавливает `serversecuritygo.service`, включает и запускает службу, затем проверяет `/healthz`.
5. Создаёт ссылку `/usr/local/bin/serversecuritygo`, чтобы интерфейс открывался одной командой.

Если нет `git` или `curl`, установщик ставит их через `apt-get`. Других изменений в системе нет, чужие каталоги в `/opt` он не трогает.

Где что лежит:

| Что | Где |
|---|---|
| Код и бинарник | `/opt/serversecuritygo`, `/opt/serversecuritygo/bin/serversecuritygo` |
| Настройки | `/opt/serversecuritygo/.env` (права 600, в git не попадает) |
| Исключения (необязательно) | `/opt/serversecuritygo/allowlist.json` |
| История и метрики | `/var/lib/serversecuritygo` (права 700): `state.json`, `events.jsonl`, `audit-baseline.json`, `metrics.json` |
| Резервные копии | `/var/backups/serversecuritygo` (права 700) |
| Логи | journald: `journalctl -u serversecuritygo` |
| systemd-юнит | `/etc/systemd/system/serversecuritygo.service` |
| Команда запуска | `/usr/local/bin/serversecuritygo` (ссылка на бинарник) |
| Сокет для терминального интерфейса | `/run/serversecuritygo/api.sock` (права 600, только root; создаётся при запуске службы) |

Ручная установка без скрипта:

```bash
git clone https://github.com/Zagorsky17/ServerSecurityGo /opt/serversecuritygo
cd /opt/serversecuritygo
make build          # или скачайте бинарник релиза в bin/serversecuritygo
install -m 600 .env.example .env
install -m 644 deploy/serversecuritygo.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now serversecuritygo
```

Слева десять панелей: сводка, подозрительные процессы, все процессы (списком или деревом), сетевые соединения, открытые порты, результаты аудита, история, системные проверки, метрики сервера и сетевая нагрузка. Если установлен fail2ban, перед историей появляется ещё одна панель — fail2ban, и номера следующих панелей сдвигаются; если сбор метрик выключен, панелей метрик и сетевой нагрузки нет. К панелям с номером больше десяти переходят клавишей `Tab`. Справа подробности выбранного элемента: оценка риска с объяснением, признаки с фактами, рекомендации, командная строка, цепочка запуска, сокеты, открытые файлы и история процесса. Клавиша `L` переключает язык интерфейса: русский / английский.

| Клавиши | Действие |
|---|---|
| `1`…`9`, `0` (десятая панель), `Tab` / `Shift+Tab` | перейти к панели |
| `↑` `↓` / `j` `k`, `PgUp` `PgDn`, `g` `G` | выбор строки; в подробностях — прокрутка |
| `Enter` / `→`, `Esc` / `←` | перейти в подробности и обратно |
| `/` | фильтр панели: имя, PID, путь, пользователь, признак, уровень риска |
| `s`, `t`, `K` | сортировка процессов (риск, CPU, память, PID, имя), дерево, потоки ядра |
| `r`, `p` | просканировать сейчас (на панели «Результаты аудита» — запустить аудит сейчас), пауза автообновления |
| `y` | копировать главное значение выбранного элемента в буфер обмена вашего компьютера (OSC 52, работает по SSH): командную строку процесса, команду исправления проверки аудита, IP бана fail2ban, адрес:порт открытого порта, удалённый IP соединения |
| `c` | меню копирования: всё из подробностей — IP, команды, пути, факты, рекомендации; `Enter` или `1`…`9` копирует пункт |
| `Y` | копировать выбранный элемент в виде JSON |
| `v` | текстовый режим: подробности обычным текстом без рамок, цвета и переносов, чтобы выделить мышью; любая клавиша — вернуться в интерфейс |
| `m` | выключить и включить мышь; пока она выключена, работает обычное выделение текста терминалом |
| `+` / `z` | развернуть активную сторону на весь экран (повторное нажатие — вернуться) |
| `w` | окно графиков на панели «Метрики»: час → сутки → 30 дней |
| `L` | язык интерфейса: русский / английский |
| `?`, `q` | справка, выход |

Работает и мышь: клик выбирает панель и строку, колесо прокручивает. Пока мышь у интерфейса, терминал не выделяет текст: нажмите `m`, чтобы вернуть мышь терминалу (или зажмите `Option` в iTerm2, `Shift` — в большинстве терминалов Linux и Windows Terminal), либо откройте текстовый режим `v`.

**Откуда берутся данные.** Если служба запущена, интерфейс подключается к ней через Unix-сокет `/run/serversecuritygo/api.sock`. Доступ к сокету есть только у root, поэтому пароль и туннель не нужны, а видна вся накопленная история. Если служба не запущена или установлена старая версия без сокета, интерфейс сканирует процессы сам, и тогда история хранится только на время сеанса. Источник указан в панели «Сводка».

```bash
serversecuritygo tui --local            # всегда сканировать самостоятельно
serversecuritygo tui --refresh 2s       # обновлять экран чаще
```

Чтобы видеть процессы всех пользователей, запускайте интерфейс от root (в режиме службы данные и так собирает служба).

Если копирование клавишами `y` и `c` не срабатывает: OSC 52 поддерживают iTerm2, kitty, WezTerm, Alacritty, Windows Terminal и современные xterm. В tmux нужна настройка `set -g set-clipboard on`. Terminal.app на macOS OSC 52 не поддерживает: нажмите `v` (текстовый режим) и выделите текст мышью — длинную команду терминал перенесёт сам и скопирует одной строкой.

## Веб-панель (по желанию)

Веб-панель повторяет те же данные в браузере. Она слушает только `127.0.0.1:8090`. С вашего компьютера её открывают через SSH-туннель:

```bash
ssh -L 8090:127.0.0.1:8090 root@<IP-сервера>
# затем в браузере: http://127.0.0.1:8090
```

Если вы подключаетесь по отдельному ключу, добавьте `-i ~/.ssh/<ключ> -o IdentitiesOnly=yes`.

Панель не обязана работать постоянно: `SSG_LISTEN_ADDR=off` в `.env` и `systemctl restart serversecuritygo` выключают её совсем — HTTP-порт не открывается, а сканирование, история, аудит и метрики продолжаются, и всё это видно в терминальном интерфейсе. Чтобы вернуть панель, впишите адрес обратно и перезапустите службу.

Пока пароль не задан, служба пускает в панель только root: для каждого подключения к `127.0.0.1` она смотрит владельца сокета в `/proc/net/tcp`. Туннель под root работает, а другие пользователи сервера (например, взломанный `www-data`) получат ошибку 403. Если вы заходите по SSH под своим пользователем, добавьте его UID в `SSG_LOCAL_UIDS` (например, `0,1000`) или задайте пароль.

## Возможности

**Сбор данных** идёт из `/proc` и связанных источников:

| Данные | Источник |
|---|---|
| PID, PPID, имя, состояние, потоки, время запуска, CPU (utime+stime) | `/proc/PID/stat` |
| UID/EUID/GID, RSS, PID в пространствах имён | `/proc/PID/status` |
| Командная строка (секреты маскируются) | `/proc/PID/cmdline` |
| Исполняемый файл, признак удаления, права, владелец | `/proc/PID/exe` (readlink + stat) |
| Рабочий каталог | `/proc/PID/cwd` |
| Открытые файлы и сокеты | `/proc/PID/fd/*` |
| TCP/UDP/Unix-сокеты по каждому сетевому пространству имён | `/proc/PID/net/{tcp,tcp6,udp,udp6,unix}` |
| Пространства имён и контейнеры (docker, containerd, kubernetes, podman, lxc) | `/proc/PID/ns/*`, `/proc/PID/cgroup` |
| Наличие `LD_PRELOAD`/`LD_AUDIT` (только имена, значения не хранятся) | `/proc/PID/environ` |
| Пользователи | `/etc/passwd` |
| Адреса сервера (чтобы отличить публичные порты от частных) | `/proc/net/fib_trie`, `/proc/net/if_inet6` |
| Состояние и правила ufw | `/etc/ufw/ufw.conf`, `/etc/default/ufw`, `/etc/ufw/user.rules`, `/etc/ufw/user6.rules` |
| Настройки SSH | `/etc/ssh/sshd_config` с `Include` и `Match`, права `/etc/ssh/ssh_host_*_key` |
| Учётные записи (хеши паролей не показываются и не сохраняются — только тип алгоритма) | `/etc/passwd`, `/etc/shadow`, `/etc/group`, `/etc/login.defs`, `/etc/environment`, `.profile` и `.bashrc` пользователя root |
| Правила sudo | `/etc/sudoers` с `@include`/`@includedir`, алиасами и `Defaults` |
| Опубликованные порты Docker, имя и образ контейнера | аргументы `docker-proxy`, `<data-root>/containers/*/config.v2.json` (переменные окружения не попадают в структуры в памяти и нигде не показываются) |
| Время загрузки, ОЗУ, ядро | `/proc/stat`, `/proc/meminfo`, `/proc/sys/kernel/osrelease` |
| Метрики сервера | `/proc/stat`, `/proc/loadavg`, `/proc/meminfo`, `/proc/pressure/*`, `/proc/diskstats`, `/proc/net/dev`, `/proc/uptime`, `/proc/vmstat`, `/proc/self/mounts` + `statfs` |

Системные проверки закрепления: `/etc/ld.so.preload`, cron (`/etc/crontab`, `/etc/cron.*`, `/var/spool/cron`), systemd-юниты в `/etc/systemd/system`, `/etc/rc.local`, `/etc/init.d`, `/etc/profile.d`, `.bashrc`, `update-motd.d`, `authorized_keys`.

**Терминальный интерфейс** описан [выше](#терминальный-интерфейс). **Веб-панель** (русский и английский интерфейс, светлая и тёмная тема):

1. **Подозрительные** — процессы с признаками, отсортированные по риску. Для каждого показаны признаки, баллы, первое и последнее наблюдение и рекомендация.
2. **Все процессы** — поиск, сортировка по любому столбцу, фильтры по PID/PPID, пользователю, имени, пути и минимальному уровню риска.
3. **Дерево** — родительские и дочерние связи, сворачивание веток, подсветка найденного.
4. **Сеть** — сокеты с процессами-владельцами, фильтры по протоколу, состоянию и внешним адресам.
5. **Открытые порты** — что слушает сервер и откуда это доступно; см. [Открытые порты](#открытые-порты).
6. **Результаты аудита** — аудит SSH, учётных записей, sudo и параметров ядра; см. [Результаты аудита](#результаты-аудита).
7. **История** — запуск, завершение, смена exe, cmdline или пользователя, рост и снижение риска, новые признаки, новые слушающие порты, системные находки, изменения настроек безопасности.
8. **Система** — сведения о сервере, ограничения сканирования (права, контейнер), проверки закрепления и опасные открытые порты.
9. **Метрики** — загрузка процессора и steal, нагрузка, PSI, память, диски и сеть с графиками за час, сутки и 30 дней; см. [Метрики сервера](#метрики-сервера).
10. **Сетевая нагрузка** — полуоткрытые соединения по портам, источники соединений, счётчики ядра и признаки атаки; см. [Сетевая нагрузка и признаки DDoS](#сетевая-нагрузка-и-признаки-ddos).
11. **Карточка процесса** — все собранные данные, объяснение оценки, факты по каждому признаку, рекомендации, цепочка предков, потомки, сокеты, открытые файлы и история процесса. Командную строку и JSON карточки можно скопировать, на карточку можно дать прямую ссылку (`#p=<ключ>`).

Панель обновляется автоматически, интервал от 5 до 60 секунд, можно выключить. Пока открыта карточка, автообновление приостанавливается.

### Открытые порты

Самая частая реальная причина взлома VPS — сервис, который случайно слушает `0.0.0.0`: Redis без пароля, MongoDB, Docker API, панель администратора. Вкладка **«Открытые порты»** (панель `5` в терминальном интерфейсе, `GET /api/exposure`, таблица в конце вывода `serversecuritygo scan`) показывает каждый слушающий TCP-сокет и привязанный UDP-сокет:

- **доступность**: *публичный* (любой адрес вне диапазонов ниже, включая `0.0.0.0` и `::` — все интерфейсы; рядом перечислены публичные адреса сервера), *частная сеть* (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `fc00::/7`, link-local), *только локально* (`127.0.0.0/8`, `::1`) или *внутри контейнера* (сокет в своём сетевом пространстве имён: снаружи доступен только через опубликованный порт);
- процесс-владелец, пользователь и контейнер; для Docker — имя контейнера, образ и проброс портов;
- **узнанный сервис** из встроенной таблицы: Redis, Docker API, MongoDB, Elasticsearch/OpenSearch, etcd, kubelet, Jupyter, memcached, PostgreSQL, MySQL/MariaDB, RabbitMQ, CouchDB, SMB, RDP, VNC, Telnet, FTP, rpcbind, NFS, SNMP, экспортеры Prometheus, а также публичные UDP-сервисы, которыми усиливают DDoS (DNS, NTP, SSDP/UPnP, chargen, CLDAP, WS-Discovery). Сервис узнаётся по порту и имени процесса (или образу контейнера); совпадение только по номеру порта снижает уровень на ступень: на порту может работать другая программа;
- состояние **ufw** для порта: *открыт* (разрешающее правило для любых адресов), *закрыт* (ufw включён и не разрешает порт всем) или *в обход ufw*.

Уровень — опасность доступности сервиса, а не признак взлома: Redis из интернета — CRITICAL, PostgreSQL — HIGH, экспортер Prometheus — LOW. Если порт закрыт ufw, уровень снижается до LOW с пояснением, что сервис защищает только межсетевой экран. Каждый опасный публичный порт становится системной находкой с этим уровнем (она видна во вкладке «Система», в истории и в журнале) и признаком категории `exposure` в карточке процесса, который держит порт. Этот признак не «сильный»: сам по себе он поднимает легитимный процесс не выше LOW.

**Docker в обход ufw.** Docker добавляет свои правила iptables раньше правил ufw, поэтому `ufw deny 6379` не закрывает порт, опубликованный как `-p 6379:6379`. Если ufw включён, а порт контейнера опубликован на всех интерфейсах без разрешающего правила ufw, панель сообщает `fw_docker_bypass` (HIGH) и предлагает публиковать порт как `127.0.0.1:ПОРТ:ПОРТ` или ограничить его в цепочке `DOCKER-USER`. Опубликованные порты читаются из аргументов `docker-proxy` и из `config.v2.json` контейнеров, поэтому видны и при `userland-proxy: false`. Docker API не используется: его сокет даёт root, а наблюдателю он не нужен.

Чтобы не получать находку о намеренно открытом порте, добавьте правило allowlist для процесса с ID признака (например, `{"exe": "/usr/lib/postgresql/16/bin/postgres", "rules": ["exposed_database"]}`): признак процесса и системная находка будут показаны как подавленные и перестанут учитываться. Порты, опубликованные Docker без слушающего процесса (`userland-proxy: false`), так подавить нельзя.

### Результаты аудита

Большинство взломов VPS происходит не через уязвимости нулевого дня, а через вход по паролю, лишний `NOPASSWD: ALL` или забытого пользователя. Вкладка **«Результаты аудита»** (панель `6` в терминальном интерфейсе, `GET /api/audit`, команда `serversecuritygo audit`) проверяет конфигурацию — причины взлома, а не его следы.

Служба выполняет аудит сразу при запуске, затем каждые `SSG_AUDIT_INTERVAL` (по умолчанию час). Кнопка **«Проверить сейчас»** (`r` на панели в терминальном интерфейсе) запускает его немедленно — например, после исправления; пока идёт проверка, новая не запускается. На вкладке видно, когда была последняя проверка и сколько пройдено: «пройдено N из M» считает только проверки с результатом «в порядке», «опасно» или «требует внимания» (советы, «неприменимо» и «нет данных» не учитываются).

У каждой проверки есть результат (*в порядке*, *опасно*, *требует внимания*, *совет*, *неприменимо* — например, sshd не установлен, *нет данных* — нет прав на чтение), важность, факты с файлом и строкой (`/etc/ssh/sshd_config.d/50-cloud-init.conf:1 PasswordAuthentication yes`), рекомендация и часто готовая команда исправления. Приложение команду не выполняет: её запускаете вы. Перед изменением SSH проверьте вход по ключу в отдельной сессии.

| Группа | Проверки |
|---|---|
| SSH | `ssh_root_login`, `ssh_password_auth`, `ssh_empty_passwords`, `ssh_kbd_interactive` (пароль через PAM даже при `PasswordAuthentication no`), `ssh_max_auth_tries`, `ssh_x11_forwarding`, `ssh_tcp_forwarding` (`GatewayPorts`), `ssh_weak_crypto` (CBC, 3DES, RC4, MD5, SHA-1, DSA), `ssh_authkeys_file` (нестандартный файл ключей или `AuthorizedKeysCommand`), `ssh_host_keys_perms`, `ssh_config_perms`, советы `ssh_allow_users`, `ssh_banner_version`, `ssh_port` |
| Учётные записи | `acct_uid0_extra`, `acct_empty_password`, `acct_service_shell`, `acct_weak_hash` (MD5, DES), `acct_new`, `acct_priv_groups` (`sudo`, `admin`, `wheel`, `docker`, `lxd`, `disk`, `adm`, `shadow`), `acct_duplicate_ids`, `acct_passwd_perms`, `acct_home_perms`, `acct_root_path` |
| sudo | `sudo_nopasswd_all` (MEDIUM для облачных пользователей по умолчанию `ubuntu`, `debian`, `admin`…), `sudo_no_auth`, `sudo_gtfobins` (`vim`, `less`, `find`, `systemctl` и другие, из которых легко выйти в root-оболочку), `sudo_wildcard`, `sudo_writable_cmd`, `sudo_env_keep` (`LD_PRELOAD`, `PYTHONPATH`, `!env_reset`), `sudo_files_perms`, `sudo_changed` |
| Ядро | Готовность к сетевой атаке: `net_syncookies`, `net_conntrack_max` (переполненная таблица отслеживания соединений отбрасывает новые соединения), `net_icmp_broadcast` (усиление smurf), советы `net_syn_backlog`, `net_somaxconn`, `net_synack_retries`, `fw_ssh_ratelimit` (правило `ufw limit` для порта SSH или jail fail2ban). Значения берутся из `/proc/sys`; команда исправления дописывает параметр в `/etc/sysctl.d/90-hardening.conf`. Если модуль conntrack не загружен, проверка неприменима |

Настройки sshd разбираются так, как их читает сам sshd: `Include` раскрывается на месте, для ключа действует первое значение, блоки `Match` показываются отдельно («для пользователя X разрешён вход по паролю»), отсутствующие ключи берут значения OpenSSH по умолчанию. Разбор sudoers понимает `@include`/`@includedir` (файлы с точкой в имени пропускаются, как у sudo), алиасы, перенос строк и `Defaults`.

**Изменения.** Служба запоминает имена и UID пользователей, членов привилегированных групп и SHA-256 файлов sudoers в `/var/lib/serversecuritygo/audit-baseline.json` (права 600, без паролей и содержимого файлов). Новый пользователь, новый член привилегированной группы или правка sudoers переводят `acct_new`, `acct_priv_groups` или `sudo_changed` в «опасно» на сутки — следующий запуск не погасит тревогу молча. Если файл в каком-то запуске не прочитался, его часть базовой линии сохраняется, и потом ничего не окажется «новым». Каждое изменение результата («было в порядке — стало опасно», «исправлено») записывается во вкладку «История» и в журнал. Разовой команде `serversecuritygo audit` сравнивать не с чем, поэтому проверки изменений в ней «неприменимы».

### fail2ban

Вкладка **«fail2ban»** (панель в терминальном интерфейсе, `GET /api/fail2ban`) появляется, только если fail2ban установлен: есть `/etc/fail2ban` и `fail2ban-server` (или пакет dpkg) либо работает процесс `fail2ban-server`. Без fail2ban нет ни вкладки, ни панели, ни пустой заглушки; API отвечает `{"installed": false}`.

Что показывается за последние `SSG_AUTH_LOG_DAYS` дней (по умолчанию 14):

- состояние: запущен ли, версия, включённые jail с `maxretry`, `findtime`, `bantime` (и `bantime.increment`) и файлом, в котором jail включён; конфигурация читается так же, как её читает fail2ban: `jail.conf`, `jail.d/*.conf`, `jail.local`, `jail.d/*.local`, с `[DEFAULT]` и подстановкой `%(имя)s`;
- текущие баны: IP, jail, с какого времени, до какого (или навсегда), сколько раз этот адрес уже банили (рецидивисты) и готовая команда `fail2ban-client set <jail> unbanip <IP>` — приложение её не выполняет;
- интенсивность перебора паролей: попытки (строки `Found`) и баны по дням и по часам (графики в панели, мини-графики из блочных символов в терминале), итоги за сутки и за период, пиковый час;
- самые активные адреса и подсети /24 (/64 для IPv6) с несколькими атакующими адресами; адреса из `ignoreip`, которые продолжают перебор, помечены;
- последние события: баны, разбаны, восстановленные и продлённые баны, перезапуски fail2ban и jail.

Данные берутся только из файлов: `/var/log/fail2ban.log` (путь — из `logtarget` в `fail2ban.conf`/`fail2ban.local`) и его ротированных копий, в том числе `.gz`. `fail2ban-client` не вызывается. Ротированные файлы разбираются один раз, текущий дочитывается с места, где остановились; сводка пересчитывается, только когда изменился журнал, конфигурация или состояние fail2ban (иначе — не чаще раза в минуту). Счётчики старше периода забываются. Текущие баны восстанавливаются по журналу (бан без последующего разбана с учётом `bantime`; перезапуск fail2ban снимает все баны до строк `Restore Ban`); точный список — `fail2ban-client status sshd`. IP-адреса — персональные данные: они хранятся только в памяти службы и не пишутся ни в `state.json`, ни в историю событий. Объём разбора ограничен (256 МБ на файл, 200 000 разных адресов на все файлы), поэтому журнал сервера под сильным перебором не исчерпает память службы.

Перебор на публичном сервере идёт постоянно, поэтому статистика справочная и на оценку процессов не влияет. Системные проверки:

| ID | Уровень | Когда |
|---|---|---|
| `fail2ban_not_running` | MEDIUM | fail2ban установлен, но `fail2ban-server` не запущен: защита от перебора выключена |
| `fail2ban_sshd_disabled` | LOW | SSH доступен из интернета, а ни один включённый jail его не защищает |
| `fail2ban_log_unavailable` | INFO | журнал пишется в journald/syslog (`logtarget = SYSTEMD-JOURNAL`) или файл не читается |

`fail2ban_sshd_disabled` можно подавить правилом allowlist для процесса `sshd`.

### Метрики сервера

Вкладка **«Метрики»** (панель `10` в терминальном интерфейсе, `GET /api/metrics?range=1h|24h|30d`) отвечает на вопрос «почему сервер тормозит»: из-за ваших процессов, из-за нехватки памяти или из-за хостера. Раздел появляется, только когда служба собирает метрики (`SSG_METRICS_ENABLED=true`).

Что снимается каждые `SSG_METRICS_INTERVAL` (по умолчанию 5 с) отдельной лёгкой горутиной — чаще, чем идёт сканирование процессов, иначе всплеск длиной полминуты был бы не виден:

- **процессор** по составляющим (пользователь, система, ожидание диска, **steal**) — всего и по ядрам; steal — это время, которое гипервизор отдал другим виртуальным машинам, пока ваша ждала процессор: при стабильном steal сервер медленный не из-за ваших процессов. На голом железе steal всегда 0, и панель прямо пишет, что это не виртуальная машина;
- **средняя нагрузка** 1/5/15 относительно числа ядер и **давление PSI** (`/proc/pressure/*`, доля времени, когда задачи ждали процессор, память или диск); на ядрах до 4.20 или при `psi=0` блок просто отсутствует;
- **память и swap**, **заполненность разделов** (включая inode), **ввод-вывод дисков** (МБ/с и загруженность устройства), **трафик интерфейсов** (МБ/с, пакеты/с, отбросы), **uptime**;
- всё — только из `/proc` и `statfs`: ни одной внешней команды, ни одного исходящего соединения. Сетевые разделы (NFS, CIFS, sshfs) не измеряются: `statfs` на недоступном сервере завис бы вместе с горутиной метрик.

Ряды хранятся в памяти с понижением детализации: **час** — каждый замер, **сутки** — по минуте, **30 дней** (`SSG_METRICS_RETENTION`) — по 15 минут. Для каждой точки хранятся среднее и максимум, поэтому короткий всплеск не исчезает при усреднении (на графике он виден как бледная заливка над линией). Агрегаты пишутся в `/var/lib/serversecuritygo/metrics.json` раз в пять минут и при остановке, поэтому графики за сутки и месяц переживают перезапуск службы; сырые замеры на диск не сохраняются. Повреждённый файл не мешает запуску: он отодвигается в `.corrupt`, ряды начинаются заново.

Внутри контейнера `/proc/stat` и `/proc/meminfo` показывают хост, а не лимиты контейнера — об этом есть пометка в интерфейсе.

Метрики **не влияют** на оценку риска процессов: перегруженный сервер — вопрос качества VPS, а не взлома. Но признаки из них попадают в раздел «Система», в историю событий и в отчёт `scan`:

| ID | Уровень | Когда |
|---|---|---|
| `steal_high` | LOW | steal выше `SSG_STEAL_THRESHOLD` (10 %) дольше 10 минут: хостер перепродал ресурсы |
| `disk_almost_full` | MEDIUM | раздел или его inode заполнены больше `SSG_DISK_FULL_THRESHOLD` (90 %): на заполненном диске перестают писаться журналы — разбираться во взломе будет не по чему |
| `load_high` | INFO | средняя нагрузка больше двух на ядро дольше 15 минут |
| `memory_pressure` | INFO | PSI памяти выше 10 % или swap вырос больше чем на 64 МБ за 10 минут |
| `oom_recent` | LOW | вырос счётчик `oom_kill` в `/proc/vmstat`: ядру не хватило памяти и процесс был убит |

Признак появляется только после удержания (10–15 минут) и снимается, как только условие пропало: один всплеск тревогой не считается. Поэтому в разовом `serversecuritygo scan` из этих признаков виден только `disk_almost_full`: остальным нужна работающая служба, которая снимает метрики постоянно.

### Сетевая нагрузка и признаки DDoS

Вкладка **«Сетевая нагрузка»** (панель `11` в терминальном интерфейсе, `GET /api/netload`) отвечает на вопрос «сервер не отвечает — это атака или приложение?». Раздел появляется вместе с метриками (`SSG_METRICS_ENABLED=true`): счётчики ядра снимает та же горутина.

**Границы.** Приложение только наблюдает: оно не блокирует адреса, не меняет правила межсетевого экрана и не создаёт нагрузку. Нагрузочного тестирования в нём нет: слать поток запросов значит сделать инструмент атаки. И главное — **объёмную атаку, которая забивает канал до сервера, изнутри не видно совсем**: сервер видит только то, что до него дошло. От такой атаки защищают хостер и CDN, и приложение говорит об этом прямо, а не обещает «защиту».

Что видно:

- **порты**: полуоткрытые соединения (`SYN_RECV`, `NEW_SYN_RECV` — начатое и не завершённое рукопожатие), установленные соединения, очередь принятия соединений и её предел (`backlog` из `tx_queue:rx_queue` слушающего сокета), число разных адресов и процесс-владелец;
- **источники**: отдельные адреса и подсети (/24 для IPv4, /64 для IPv6) с числом соединений, полуоткрытых и адресов; доверенные сети и частные сети помечены;
- **счётчики ядра** за секунду: SYN cookies, отбросы на слушающих сокетах, отбросы на приёме, ошибки UDP, повторные передачи, пакеты, установленные соединения, сокеты без владельца, заполненность таблицы conntrack. Те же счётчики попадают в ряды метрик (`net_syn_rate`, `net_listen_drops`, `net_conntrack`, `net_rx_drops`, `net_udp_errors`, `net_estab`, `net_orphan`, `net_retrans`) и видны на графиках за час, сутки и 30 дней.

Источники данных — только `/proc`: `net/netstat`, `net/snmp`, `net/sockstat`, `net/softnet_stat`, `net/stat/nf_conntrack`, `net/dev`, `sys/net/*` и таблицы `net/tcp`, `net/tcp6`. Внешних баз репутации адресов нет и не будет (правило автономности).

| ID | Уровень | Когда |
|---|---|---|
| `net_syn_flood` | MEDIUM; HIGH при полуоткрытых ≥ 90 % backlog или отбросах SYN | SYN cookies > 50/с дольше 30 с **или** ≥ 256 полуоткрытых и ≥ 50 % backlog на порту (два сканирования подряд) |
| `net_listen_overflow` | MEDIUM | `ListenOverflows`/`ListenDrops` > 10/с дольше минуты **или** очередь accept ≥ 90 % backlog: приложение не успевает принимать соединения — атака или нехватка воркеров |
| `net_conn_flood_ip` | LOW; MEDIUM при > 5 × порога | один адрес держит больше `SSG_NET_CONN_PER_IP` (200) соединений, два сканирования подряд |
| `net_conn_flood_subnet` | MEDIUM | одна подсеть держит > 4 × порога соединений с ≥ 20 разных адресов |
| `net_conn_surge` | LOW | входящих соединений ≥ 1000 и ≥ `SSG_NET_SURGE_FACTOR` × обычного (нужна база за шесть часов) |
| `net_conntrack_full` | MEDIUM; HIGH при ≥ 95 % или потерях | таблица conntrack заполнена ≥ 80 % дольше минуты: ядро начинает отбрасывать новые соединения |
| `net_orphans_high` | LOW | сокетов без владельца ≥ 50 % `tcp_max_orphans` или растёт `TCPAbortOnMemory` |
| `net_udp_flood` | MEDIUM / LOW | `RcvbufErrors` > 100/с (приложение не успевает читать UDP) или `NoPorts` > 1000/с (поток на закрытые порты) |
| `net_rx_drops` | MEDIUM | отбросы на приёме > 1000/с: ядро или сетевая карта не успевают |
| `net_pps_surge` | LOW | входящих пакетов ≥ 50 000/с и ≥ `SSG_NET_SURGE_FACTOR` × обычного |
| `net_ddos_suspected` | HIGH | сработали признаки минимум из **двух групп** (SYN, соединения, ядро, UDP) — один симптом даёт и наплыв настоящих посетителей |
| `net_table_truncated` | INFO | соединений больше `SSG_NET_MAX_SOCKETS`: числа в разделе занижены |

**Удержание и гистерезис.** Признак появляется, только если условие держится 30–120 секунд (или два сканирования подряд для признаков по соединениям), и снимается через пять минут без превышения. Один всплеск тревогой не считается, а во время атаки признак не мигает и не засыпает историю событиями.

**Ложные срабатывания.** У сайта за CDN все посетители приходят с адресов CDN — впишите их диапазоны в `SSG_NET_TRUSTED_NETS`, и они перестанут считаться источниками флуда (в таблице они помечены как доверенные). Для частных сетей и для подсетей порог автоматически в четыре раза выше. Исходящие соединения сервера в источники не попадают, как и соединения с самим собой. Относительные пороги («в N раз больше обычного») не применяются, пока метрик меньше шести часов. Любой признак можно подавить правилом allowlist по его ID.

**Защита самого сканера.** Во время атаки `/proc/net/tcp` разрастается до сотен тысяч строк, поэтому число сокетов на одно сетевое пространство имён ограничено `SSG_NET_MAX_SOCKETS` (100 000, около 200 байт на сокет); сверх предела сокеты пропускаются и появляется `net_table_truncated`. Агрегаты по адресам тоже ограничены по размеру.

### UFW и время обхода PID

Раздел **UFW** расположен после fail2ban (если fail2ban отсутствует — после аудита). Он показывает сохранённые политики входящего, исходящего и маршрутизируемого трафика, IPv6, журналирование, профили приложений, модули conntrack и файл sysctl. Можно открыть полный текст `ufw.conf`, `/etc/default/ufw`, `before/user/after.rules` и их IPv6-вариантов, `before/after.init`, `sysctl.conf`, файла из `IPT_SYSCTL` и профилей `applications.d`. В TUI выберите файл, нажмите Enter для прокрутки подробностей; `/` фильтрует по пути и содержимому, `y` копирует путь, `Y` — JSON. В веб-панели раскройте файл. API: `GET /api/ufw`, с той же авторизацией, что у остальных разделов.

Это конфигурация на диске: её изменения могут ещё не быть применены. Активные правила ядра и сторонние правила Docker здесь не проверяются. Файлы читаются без выполнения команд, максимум 1 МиБ на файл, 4 МиБ суммарно и 1000 профилей; ошибки, превышение лимитов и отсутствующие обязательные файлы показываются явно. Отсутствующая настройка не заменяется выдуманным значением по умолчанию. [Порядок обработки UFW](https://manpages.ubuntu.com/manpages/noble/man8/ufw-framework.8.html): before → user → after, отдельно для IPv4 и IPv6.

Во время полного обхода PID предупреждение показывает прошедшее время, приблизительный остаток и процент диапазона. Время — `ЧЧ:ММ:СС`; остаток рассчитывается по средней скорости текущего прохода и меняется вместе с нагрузкой. До получения первых данных выводится «рассчитывается». При отмене или ошибке время замораживается; новый проход начинает отсчёт заново. Отображение обновляется с очередным снимком сканера (`SSG_SCAN_INTERVAL`), а успешный результат содержит итоговую длительность.

### Скрытые процессы, модули ядра и целостность пакетов

Результаты появляются в **«Системе»**, истории и отчётах `scan`. Служба сопоставляет список `/proc` с TGID потоков и родительскими PID, затем дважды с паузой 50 мс проверяет отсутствующего лидера процесса по PID и времени запуска. Обычные потоки, завершившиеся процессы и повторно использованные PID исключаются. Отдельный обработчик перебирает все номера PID порциями по 1024 с паузой 100 мс; следующий обход начинается через `SSG_ROOTKIT_INTERVAL` (по умолчанию `10m`). Большой диапазон PID занимает несколько минут; короткоживущие процессы могут быть пропущены. Число задач из `loadavg` не используется как доказательство скрытия: пространства имён и параллельное создание задач делают такой вывод ненадёжным.

Проверка модулей дважды сопоставляет `/proc/modules` с загружаемыми модулями в состоянии live из `/sys/module`. Встроенные модули и переходные состояния загрузки/выгрузки исключаются. `rootkit-modules.json` хранит первоначальный набор модулей для текущей загрузки ОС. У `kmod_hidden` и `hidden_process` уровень CRITICAL; у `kmod_new` и `kmod_unsigned` — MEDIUM. Для известных внешних драйверов `kmod_unsigned` снижается до LOW, но имя не доказывает доверие. `kernel_tainted` — справочная запись: [флаги taint ядра](https://docs.kernel.org/admin-guide/tainted-kernels.html) также описывают предупреждения, аппаратные сбои и внешние драйверы. `kmod_unindexed` и `kmod_origin_unavailable` означают отсутствие записи в `modules.dep` или недоступность индекса. Они не доказывают фактический путь загрузки модуля.

Служба проверяет выбранные файлы пакетов при запуске и каждые `SSG_INTEGRITY_INTERVAL` (по умолчанию `24h`), со скоростью чтения до 16 МиБ/с. Область проверки: `/usr/bin`, `/usr/sbin`, `/bin`, `/sbin`, бинарники systemd, модули PAM, вспомогательные программы OpenSSH, libc, libpam, libkeyutils и libaudit, включая usrmerge и каталоги библиотек разных архитектур. Данные status, `.list`, `.md5sums`, conffiles и diversions читаются непосредственно из dpkg; ссылки alternatives не считаются непакетными обычными исполняемыми файлами. Занятая или меняющаяся база dpkg даёт неполный результат. Файлы без контрольной суммы пакета явно отмечаются как непроверенные.

У `bin_modified` уровень CRITICAL для SSH, инструментов повышения привилегий и входа, распространённых средств диагностики, PAM и libc; для остальных расхождений — HIGH. `integrity.json` сохраняет SHA-256 после первой успешной проверки службой после установки. При согласованной смене версии пакета эталон обновляется; при смене хеша или метаданных в той же версии прежний эталон сохраняется и появляется находка. `bin_unpackaged` имеет уровень INFO. После независимой проверки вручную установленного файла точное правило `{"exe":"/usr/bin/my-tool","rules":["bin_unpackaged"]}` принимает его SHA-256 при следующем успешном проходе после перезапуска службы. Шаблоны и правила без явного ID `bin_unpackaged` файл не принимают. Последующая смена хеша снова даёт `bin_modified`.

```bash
serversecuritygo scan --full --min-risk INFO --format json --output /root/full-scan.json
```

`--full` дожидается обхода PID и проверки файлов; выполнение можно отменить. Разовый запуск и локальный TUI читают эталоны службы, но не перезаписывают их. Быстрый `scan` оставляет эти проверки ожидающими и возвращает код **3**, в том числе с `--fail-on none`, если находка не вызвала код 1. `rootkit_unavailable`, `rootkit_sweep_pending`, `integrity_pending`, `integrity_unavailable` и `integrity_unverified` также делают отчёт неполным и выводятся в предупреждениях независимо от фильтра риска. Завершённые проходы содержат время проверки (`rootkit_sweep_complete`, `integrity_complete`). Демо не проверяет настоящий хост этими средствами.

Базовая линия устанавливает локальное доверие при первом наблюдении, а не независимо подтверждает подлинность. Root может изменить MD5, [локальную базу dpkg](https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html) и эталон SHA-256. Скомпрометированное ядро может обмануть и procfs, и sysfs. Сверка с независимо доверенным архивом `.deb` остаётся следующим этапом. Лимиты чтения явные: 100 000 записей `/proc`, 16 384 записи модулей, 64 МиБ метаданных dpkg на проход и 1 ГиБ на хешируемый файл. Превышение лимита означает неполную проверку, а не отсутствие проблем.

## Самоконтроль сканера

Служба проверяет собственную установку и свежесть данных независимо от цикла сканирования. Находки видны в «Системе», предупреждениях сводки, истории и отчётах `scan`. Самоконтроль не изменяет настройки сервера и не применяет исключения автоматически.

| Признак | Что проверяется |
|---|---|
| `self_binary_changed` — CRITICAL | SHA256 запущенного бинарника при старте не совпадает с эталоном установки. На Linux читается `/proc/self/exe`, поэтому проверяется запущенный файл, даже если его путь уже заменён. |
| `self_unit_changed` — HIGH | Изменение, появление или удаление файлов `serversecuritygo.service`, его `serversecuritygo.service.d/*.conf` и общих `service.d/*.conf` в `/etc`, `/run`, `/usr/local/lib`, `/usr/lib`, `/lib/systemd/system`. В фактах перечислены затронутые пути. |
| `self_baseline_changed` — HIGH | Эталон изменён после запуска; служба продолжает сравнение с исходным эталоном. |
| `self_allowlist_changed` — MEDIUM | Изменение, создание или удаление файла исключений. Сохраняется только его путь и SHA256, содержимое не попадает в историю. Загруженные правила действуют до перезапуска. |
| `self_scan_stalled` — HIGH | Более трёх интервалов нет успешно завершённого сканирования, включая отсутствие первого результата. Ошибка сканирования не обновляет время успеха. |
| `self_clock_back` — MEDIUM | Настенные часы отстали от монотонных более чем на секунду между проверками. Предупреждение сохраняется до перезапуска; тайм-аут сканирования не зависит от перевода часов. |
| `self_check_unavailable` — MEDIUM | Эталон отсутствует или повреждён, файл недоступен, имеет неподдерживаемый тип либо превышает лимит. Это неполная проверка, а не подтверждение целостности. |

Установка и обновление атомарно записывают `/var/lib/serversecuritygo/self.sha256` с правами `600` перед запуском службы. Этот путь фиксирован и не зависит от `SSG_DATA_DIR`. Откат возвращает прежний эталон вместе с бинарником. Служба не создаёт и не обновляет эталон сама. Для ручной установки после проверки бинарника и файлов юнита выполните из каталога проекта от root:

```bash
source scripts/lib.sh
write_self_baseline
systemctl restart serversecuritygo
```

Команда принимает текущие файлы за эталон: не запускайте её для устранения предупреждения без проверки причин изменения. Контрольная сумма не заменяет доверенную подпись релиза; атакующий с root может заменить и программу, и эталон. Проверяются файлы юнита на диске, включая перекрытые другими файлами; это не доказательство того, что systemd уже загрузил именно эту конфигурацию. Допустимые изменения администратора тоже требуют проверки.

Служба сверяет файлы не реже раза в 5 секунд при нормальной работе наблюдателя. Файл исключений должен быть обычным файлом до 1 МиБ, без симлинка; такие же ограничения действуют при загрузке правил. Состояние наблюдения за исключениями хранится в `SSG_DATA_DIR/self-allowlist.json` с правами `600`, чтобы видеть изменения между перезапусками. Разовые `scan` и локальный TUI используют память и не изменяют состояние службы. Демо не проверяет реальную установку.

`GET /api/status` содержит `stale`; `/healthz` возвращает `503` до первого успешного сканирования и при устаревших данных. Находки целостности сами по себе не делают проверку доступности неуспешной: их нужно смотреть в отчёте. В `scan` недоступный самоконтроль учитывается как неполная проверка с кодом `3`, если код `1` не имеет приоритета из-за найденного риска; даже `--fail-on none` не скрывает неполноту.

В юните включены `WatchdogSec=30s` и `NotifyAccess=main`. Служба отправляет локальные уведомления `WATCHDOG=1`, пока сканирование не устарело. После прекращения уведомлений systemd перезапускает только ServerSecurityGo; остальные процессы и сеть не изменяются. При стандартном интервале сканирования 30 секунд устаревание наступает после 90 секунд без результата, затем действует тайм-аут watchdog. Поведение протокола: [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html) и [sd_notify](https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html).

## Как считается риск

Каждое правило выдаёт **признак**, то есть набор фактов: что прочитано и откуда, например `/proc/3101/exe → /dev/shm/.x/kworkerds`. Сам признак ничего не утверждает о вредоносности. У признака есть вес, категория и пометка «сильный», если он сам по себе редко бывает легитимным.

1. Сумма весов задаёт базовый уровень: от 1 балла LOW, от 15 MEDIUM, от 35 HIGH, от 60 CRITICAL.
2. Уровень ограничивается **числом независимых категорий** (расположение, целостность файла, маскировка, цепочка запуска, сеть, командная строка, поведение, окружение, привилегии, закрепление):
   - одна категория и ни одного сильного признака — не выше **LOW**. Поэтому только имя, только путь или только высокая нагрузка не дают больше LOW;
   - одна категория с сильным признаком — не выше **MEDIUM**;
   - две категории и меньше двух сильных признаков — не выше **HIGH**;
   - **CRITICAL** возможен только при трёх и более категориях или при двух сильных признаках.
3. Справочные признаки (процесс в контейнере, слушает порт, недостаточно прав) показываются, но на оценку не влияют.
4. Allowlist подавляет признаки известных легитимных процессов. Подавленный признак не скрывается, а показывается зачёркнутым и упоминается в объяснении.
5. Известные легитимные случаи учтены отдельно: бинарник в `/usr`, удалённый после `apt upgrade`, получает 4 балла вместо 20; `runc` через memfd ослаблен; unix-сокет журнала на stdout служб systemd не считается reverse shell; `node`, `java` и `python` как родители оболочки дают слабый признак.

Пример объяснения из карточки:

> Итог CRITICAL: 102 балл(ов), признаков — 4, категорий — 2 (командная строка, сеть), сильных — 2. Сработали: «Ввод/вывод оболочки или интерпретатора подключён к сетевому сокету» +40 (сильный); «Командная строка содержит конструкцию reverse shell» +35 (сильный); … Это оценка по косвенным признакам, а не доказательство компрометации.

### Закрепление, память процессов и безопасность Docker

Проверки закрепления охватывают пользователей с оболочкой из `/etc/passwd`, в том числе с домашними каталогами вне `/home`: профили оболочек, cron/at/incron, systemd services/timers/user units/drop-in/generators, PAM, motd, udev, Xsession/autostart, SysV init, хуки сети/apt/logrotate, SSH rc/config и Git hooks в `/opt/*` и `/var/www/*`. Команда PAM во временном каталоге получает CRITICAL; непакетные локальные systemd/SysV-файлы показываются как инвентарь. Отрицательный вывод о принадлежности пакету допускается только при полной локальной базе dpkg. Ссылка PAM на модуль, не найденный в стандартных каталогах, получает INFO: необязательные модули могут штатно отсутствовать. Существующий непакетный модуль остаётся HIGH. Переопределения доменов репозиториев в hosts требуют проверки; DNS-адреса и пустая история оболочки сами по себе не доказывают подмену. Цели системных симлинков разрешаются внутри корня проверяемого хоста, с ограничением числа переходов. Пользовательские симлинки, ошибки доступа и превышение лимитов делают проверку неполной. Лимиты: 1 МиБ и 4096 строк на файл, 32 МиБ на скан, 4096 записей каталога, 20 000 кандидатов путей и 64 каталога модулей PAM.

Карточки процессов показывают TracerPid, имена CapEff/CapPrm/CapBnd/CapAmb, NoNewPrivs и Seccomp. Проверяются исполняемые отображения: временные/удалённые библиотеки и анонимная исполняемая память. Вес известных JIT-сред снижен. Вес удалённой библиотеки снижается, только если замена существует в корне процесса и к ней применима пакетная база хоста; чужое mount namespace исключает такое сопоставление. Ссылка на трассировщик требует совпадения PID и времени старта. Maps ограничены 1 МиБ и 256 различными исполняемыми отображениями на процесс, 32 МиБ на скан. Environ читается потоком: 8 МиБ на процесс, 32 МиБ на скан, анализ первых 4096 байт записи. Ограничения и отказ доступа видны в отчёте. Сохраняются только флаги окружения; `/proc/environ` может не отражать изменения оболочки после запуска.

Проверки Docker читают `config.v2.json` и `hostconfig.json`: 2 МиБ на файл, 32 МиБ суммарно, до 4096 контейнеров; учитывается `data-root`. Проверяются privileged, доступ к docker.sock, чувствительные пути хоста, дополнительные capabilities, пространства имён хоста, явное отключение seccomp/AppArmor, настроенный root, устройства и похожие на секреты **имена** переменных окружения. Поддерживаются строковые bind и структурированные монтирования. Остановленные контейнеры помечаются как сохранённая конфигурация. Известное имя образа управления Docker снижает находку о сокете до HIGH, но не доказывает доверие. Также проверяются права сокета и участники группы docker; ограниченный доступ только root допустим. Имя и образ контейнера добавляются к находкам процессов. Это наблюдения конфигурации, а не проверка действующей изоляции. Docker API не вызывается; метаданные безопасности containerd/Podman отложены.

Новые ID процессных правил: `ptrace_attached`, `lib_from_temp`, `lib_deleted`, `anon_exec_memory`, `history_disabled`, `prompt_command_net`, `ld_library_path_temp`, `proc_dangerous_caps`, `proc_ambient_caps`.
Новые системные ID: `systemd_unit_no_package`, `pam_exec`, `pam_module_unusual`, `library_search_path`, `sysv_no_package`, `shell_history_disabled`, `hosts_override`, `dns_configuration`, `persistence_unavailable`, `package_ownership_unavailable`, `ctr_privileged`, `ctr_docker_sock`, `ctr_host_root_mount`, `ctr_dangerous_caps`, `ctr_host_namespaces`, `ctr_no_seccomp`, `ctr_no_apparmor`, `ctr_runs_as_root`, `ctr_devices`, `ctr_secrets_in_env`, `ctr_sock_perms`, `container_unavailable`. Системные находки выводятся в существующем разделе «Система» и отчётах. Новые процессные правила поддерживают allowlist; для `systemd_unit_no_package` можно задать точный путь юнита как `exe`. Остальные новые системные и Docker-находки остаются видимыми.

Семантика источников: [документация Linux proc](https://docs.kernel.org/filesystems/proc.html), [безопасность Docker](https://docs.docker.com/engine/security/) и [seccomp Docker](https://docs.docker.com/engine/security/seccomp/).

## Ограничения обнаружения

Это эвристический инструмент для первичного анализа, а не антивирус и не EDR.

- **Руткиты уровня ядра** могут скрывать процессы, файлы и сокеты прямо в `/proc`. Сканер видит то, что показывает ядро. Пользовательские руткиты через `LD_PRELOAD` и `/etc/ld.so.preload` на сам сканер не действуют (статический бинарник Go без libc), но могут исказить вывод `ps`, `ls` и прочих утилит.
- **Снимки, а не события.** Сканирование идёт раз в `SSG_SCAN_INTERVAL` (по умолчанию 30 с), поэтому процессы, прожившие меньше интервала, могут не попасть в историю. Для полного аудита запусков нужны auditd или eBPF.
- **Нет анализа содержимого файлов:** ни сигнатур, ни хешей, ни репутации IP-адресов. Совпадения в командной строке (`stratum+tcp`, `/dev/tcp/`) ищутся по шаблонам, и их можно обойти переименованием или обфускацией.
- **Права.** Без root нельзя прочитать exe, cwd, fd и environ процессов других пользователей. То же бывает при `hidepid` на `/proc`, `kernel.yama.ptrace_scope=3` и строгих профилях AppArmor или SELinux. Сканер сообщает об этом в баннере и в карточке процесса.
- **Контейнеры.** Внутри контейнера сканер видит только его PID-пространство. Запускайте его на хосте. Пути exe и cwd процессов в контейнерах указаны внутри файловой системы контейнера, поэтому сравнение с системными путями хоста может ошибаться.
- **Ложные срабатывания** возможны у инструментов разработчика (`go run` из `/tmp`, сборки в CI), самописных служб в нестандартных каталогах, легального майнинга и установщиков вида `curl | sh`. Для них есть allowlist.
- **CPU%** считается по разнице `utime+stime` между сканированиями с `CLK_TCK=100`, как на x86_64 и arm64 в Ubuntu и Debian. При первом наблюдении процесса показывается среднее с момента запуска (отмечено `*`).
- **Сокеты** без найденного владельца (TIME_WAIT, сокеты ядра, нет прав) показываются со статусом «неизвестно». Если сокет открыт сразу у нескольких процессов (активация через systemd socket, master и worker nginx), в таблице «Сеть» указан первый найденный владелец, а в карточке каждого процесса сокет виден полностью.
- **Открытые порты** оцениваются только по адресу, на котором слушает сокет, и по ufw. Сервис на собственном частном адресе сервера (например, `172.31.5.10` в AWS или GCP) показан как *частная сеть*, хотя при 1:1 NAT провайдера он может быть доступен из интернета по публичному IP — проверьте группы безопасности у провайдера. Правила, добавленные напрямую через `iptables`/`nftables`, firewalld и облачные межсетевые экраны не читаются.
- Отсутствие полей, которых нет в старых ядрах (например, `NSpid` до 4.1), допускается: такие сведения просто не показываются.

Завершённая история ограничена 4096 записями и бюджетом 8 МиБ (строки и учёт накладных расходов). При превышении удаляются старейшие завершённые записи с событием `history_trimmed`; активные процессы сохраняются. Retention задаёт максимальный срок, а не гарантированную глубину истории. `state.json` ограничен 16 МиБ: слишком большой или небезопасный файл вызывает ошибку запуска и остаётся нетронутым. Сохраните резервную копию перед его переносом. Новые командные строки маскируются с учётом присваиваний в кавычках; старые данные и архивы автоматически не очищаются.

После изменения `.env` выполните `systemctl restart serversecuritygo`.

**Allowlist.** Скопируйте [`allowlist.example.json`](allowlist.example.json) в `/opt/serversecuritygo/allowlist.json`. В правиле задаются `exe` и `name` (шаблоны `*` и `?`), `user` и список `rules` (идентификаторы признаков). Правило без условий игнорируется, чтобы случайно не подавить всё. Имя процесса (`comm`) процесс задаёт сам, поэтому правило без `exe` срабатывает, только если имя совпадает и с именем исполняемого файла: майнер, назвавшийся `node`, под правило `{"name": "node"}` не попадёт. Для программ на интерпретаторах (например, `gunicorn` на Python) указывайте `exe`. О правилах без `exe` служба предупреждает в журнале при запуске.

## Язык

Все тексты, которые видит пользователь, есть на русском и английском: веб-панель и страница входа, терминальный интерфейс, названия признаков, доказательства, объяснение оценки, рекомендации, события истории, предупреждения сканера, вывод `scan` и `--help`, журнал службы и сообщения об ошибках.

- **Веб-панель.** Кнопка **English / Русский** в шапке (и на странице входа) переключает язык сразу, выбор запоминается в браузере. Пока пользователь не выбрал язык, панель берёт `SSG_LANG`, а если она не задана — язык браузера (`Accept-Language`).
- **Терминальный интерфейс.** Язык переключает клавиша `L`. Начальный язык — `SSG_LANG` или локаль терминала (`LC_ALL`, `LC_MESSAGES`, `LANG`).
- **Командная строка и журнал службы.** `SSG_LANG`, иначе локаль. При пустой локали, `C` или `POSIX` (обычно так у служб systemd) вывод на русском; для английского журнала службы укажите `SSG_LANG=en` в `/opt/serversecuritygo/.env`.

Сканер хранит тексты сообщениями (ключ каталога и аргументы), а строку каждый клиент собирает на своём языке, поэтому два пользователя могут одновременно смотреть один сервер на разных языках. Переводы лежат в [`internal/i18n`](internal/i18n): в `catalog_*.go` русский и английский текст стоят рядом, а тесты проверяют, что у каждого ключа есть оба перевода с одинаковыми плейсхолдерами.

**JSON API.** Текстовые поля (`title`, `evidence`, `recommendation`, `explanation`, `recommendations`, `warnings`, `details` событий) — либо простая строка (факт из системы, например путь), либо объект-сообщение `{"key": "…", "args": […]}` (`{"sep": "…", "parts": […]}` для склеенного текста). Каталог одного языка отдаётся по `GET /i18n/ru.json` или `/i18n/en.json`. `scan --format json` выводит готовый текст на языке процесса, а не объекты-сообщения. Ошибки API приходят на языке из заголовка запроса `X-SSG-Lang`.

## Удалённый доступ

Рекомендуемый способ — SSH-туннель (см. выше): ничего не открывается наружу.

Если нужен прямой доступ, служба запустится только при выполнении всех условий:

1. Задан пароль:
   ```bash
   /opt/serversecuritygo/bin/serversecuritygo hash-password
   # вставьте выведенную строку SSG_AUTH_PASSWORD_HASH=... в .env
   ```
2. Задано имя, по которому открывается панель: `SSG_ALLOWED_HOSTS=mon.example.com`.
3. Включён HTTPS: либо `SSG_TLS_CERT` и `SSG_TLS_KEY`, либо reverse proxy с HTTPS и `SSG_TRUST_PROXY_TLS=true`. Без собственного TLS приложение должно слушать loopback (`127.0.0.1` или `[::1]`), в том числе при `SSG_TRUST_PROXY_TLS=true`. Для backend на сетевом адресе требуется TLS между прокси и приложением.

Пример для nginx: приложение остаётся на `127.0.0.1:8090`, nginx отдаёт панель по HTTPS. В `.env` задайте `SSG_TRUST_PROXY_TLS=true` и пароль: при `SSG_TRUST_PROXY_TLS=true` служба без пароля не запустится, потому что сама не может проверить, открыл ли прокси её наружу.

```nginx
server {
    listen 443 ssl;
    server_name mon.example.com;
    ssl_certificate     /etc/letsencrypt/live/mon.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mon.example.com/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:8090;
        proxy_set_header Host 127.0.0.1;
        # Адрес клиента для ограничения попыток входа: без него все
        # клиенты выглядят как 127.0.0.1 и делят один счётчик.
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
```

Пароль хранится только в виде хеша PBKDF2-SHA256 (600 000 итераций). После пяти неудачных попыток вход с этого адреса (для IPv6 — с сети /64) блокируется на 15 минут. Попытка учитывается до проверки пароля, поэтому параллельные запросы лимит не обходят, а одновременно проверяется не больше двух паролей. За reverse proxy адрес клиента берётся из `X-Forwarded-For`, который выставляет прокси (см. пример выше). Сессии живут в памяти, cookie помечены `HttpOnly`, `SameSite=Strict` и `Secure`.

Дополнительно можно ограничить доступ файрволом по IP, например `ufw allow from <ваш IP> to any port 443`.

## Обновление, откат, удаление, логи

```bash
/opt/serversecuritygo/scripts/update.sh            # до последнего релиза
/opt/serversecuritygo/scripts/update.sh v0.2.0     # до указанной версии
/opt/serversecuritygo/scripts/rollback.sh          # вернуть версию до последнего обновления
/opt/serversecuritygo/scripts/logs.sh              # журнал (последние 100 строк и слежение)
/opt/serversecuritygo/scripts/logs.sh -p warning --since today
/opt/serversecuritygo/scripts/uninstall.sh         # удалить службу, файлы и историю оставить
/opt/serversecuritygo/scripts/uninstall.sh --purge # удалить также /opt/serversecuritygo и историю
/opt/serversecuritygo/scripts/uninstall.sh --full  # полная очистка (см. ниже)
```

Как обновление защищено от сбоев:

- перед обновлением история, `.env` и `allowlist.json` архивируются в `/var/backups/serversecuritygo`, хранятся 5 последних архивов;
- новый бинарник проверяется (`version`), старый сохраняется как `bin/serversecuritygo.prev`;
- после перезапуска проверяется `/healthz`; если служба не поднялась, предыдущая версия возвращается автоматически.
- после переключения исходников обновление продолжает скрипт уже новой версии, поэтому её новые шаги срабатывают сразу. Исключение — обновление с v0.1.x: там новый скрипт ещё не запускался, и ссылку `/usr/local/bin/serversecuritygo` нужно создать вручную (`ln -sfn /opt/serversecuritygo/bin/serversecuritygo /usr/local/bin/serversecuritygo`) или выполнить `update.sh` повторно.

Резервные копии не удаляются даже при `--purge`.

**Обновление до v0.3.0 (английский язык).** Запустите `update.sh` как обычно; миграция не нужна, накопленная история сохраняется. После обновления:

- веб-панель открывается на языке браузера, в шапке есть переключатель **English / Русский**; в терминальном интерфейсе язык переключает клавиша `L`;
- журнал службы остаётся на русском; для английского добавьте `SSG_LANG=en` в `/opt/serversecuritygo/.env` и выполните `systemctl restart serversecuritygo`;
- если ваши скрипты читают JSON API, учтите, что текстовые поля теперь могут быть объектами-сообщениями (см. [Язык](#язык)); `scan --format json` по-прежнему выводит готовый текст.

### Полное удаление

Удаляет приложение так, будто его на сервере никогда не было: служба и её следы в systemd, ссылка `/usr/local/bin/serversecuritygo`, `/opt/serversecuritygo`, история `/var/lib/serversecuritygo` и резервные копии `/var/backups/serversecuritygo`. Действие необратимо.

```bash
/opt/serversecuritygo/scripts/uninstall.sh --full -y
```

Если каталог `/opt/serversecuritygo` уже удалён или повреждён, ту же очистку выполняет одна команда без скриптов:

```bash
systemctl disable --now serversecuritygo 2>/dev/null; \
rm -rf /etc/systemd/system/serversecuritygo.service /etc/systemd/system/serversecuritygo.service.d; \
systemctl daemon-reload; systemctl reset-failed serversecuritygo 2>/dev/null; \
[ -L /usr/local/bin/serversecuritygo ] && rm -f /usr/local/bin/serversecuritygo; \
rm -rf /opt/serversecuritygo /var/lib/serversecuritygo /var/backups/serversecuritygo /run/serversecuritygo
```

Чего команда не трогает, и почему:

- **пакеты `git`, `curl`, `ca-certificates`.** Установщик ставит их, только если их не было, но они нужны и другим программам. Если вы уверены, что они не нужны: `apt-get remove git curl`;
- **записи в journald.** Удалить записи одной службы нельзя, не стерев журнал всей системы. Они исчезнут сами по мере ротации журнала.

Проверить, что следов не осталось:

```bash
systemctl status serversecuritygo        # Unit serversecuritygo.service could not be found.
ls -d /opt/serversecuritygo /var/lib/serversecuritygo /var/backups/serversecuritygo /usr/local/bin/serversecuritygo   # No such file or directory
```

Состояние службы: `systemctl status serversecuritygo`.

## Консольный режим и демо

Разовое сканирование, не затрагивающее историю службы:

```bash
/opt/serversecuritygo/bin/serversecuritygo scan --env-file /opt/serversecuritygo/.env
/opt/serversecuritygo/bin/serversecuritygo scan --min-risk MEDIUM --sample 2s      # точный CPU по двум замерам
/opt/serversecuritygo/bin/serversecuritygo scan --format json --min-risk INFO > scan.json
```

Разовая проверка настроек безопасности (SSH, учётные записи, sudo); `--all` показывает и пройденные проверки:

```bash
/opt/serversecuritygo/bin/serversecuritygo audit
/opt/serversecuritygo/bin/serversecuritygo audit --format json > audit.json
```

**Форматы отчёта.** `scan` и `audit` принимают `--format`:

| Формат | Для чего |
|---|---|
| `text` (по умолчанию) | терминал |
| `json` | скрипты и Ansible: стабильная схема с `schema_version`, `verdict`, `incomplete` |
| `html` | владелец сервера: один самодостаточный файл (встроенный CSS, без скриптов, светлая и тёмная тема) с итогом, сводкой, находками и рекомендациями |
| `md` | документация или тикет: таблицы Markdown, всё взятое из системы экранировано |

`--output ФАЙЛ` пишет отчёт в файл с правами 600 (в отчёте командные строки и пути) вместо вывода на экран. Файл заменяется атомарно; символическая ссылка отвергается, а в устройство вроде `/dev/null` запись идёт напрямую:

```bash
serversecuritygo audit --format html --output /root/audit.html
serversecuritygo scan --format md --output /root/scan.md
```

**Коды выхода** позволяют запускать проверки из cron, CI, Ansible или мониторинга:

| Код | Значение |
|---|---|
| `0` | нет находок уровня `--fail-on` и выше |
| `1` | есть находки уровня `--fail-on` и выше (по умолчанию `HIGH`) |
| `2` | ошибка: `/proc` не читается вовсе, сломана конфигурация, неверный флаг |
| `3` | таких находок нет, но проверка неполная: часть данных не прочитана (запустите от root) |

`--fail-on` принимает `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` или `none`. Находки важнее неполноты: код 1 возвращается, даже если часть данных не прочитана. `--fail-on none` делает код независимым от находок (остаются только 2 и 3). **Для существующих скриптов:** раньше `scan` всегда завершался с кодом 0, теперь при находках HIGH или CRITICAL — с кодом 1; где нужно прежнее поведение, добавьте `--fail-on none`. Для `scan` уровень — наивысший риск процесса или системной находки (`--min-risk` только фильтрует вывод), для `audit` — наивысшая важность проверки со статусом «опасно» или «требует внимания».

```bash
# ежедневно в 6:00: отчёт аудита в файл, письмо от cron, если что-то не так
0 6 * * * /opt/serversecuritygo/bin/serversecuritygo audit --fail-on HIGH --format md --output /root/audit.md || echo "настройки безопасности требуют внимания: /root/audit.md"
```

Демонстрационный режим на вымышленных данных работает на Linux и macOS:

```bash
go run ./cmd/serversecuritygo demo --tui   # в терминале
go run ./cmd/serversecuritygo demo         # в браузере: http://127.0.0.1:8090
```

## Безопасность

- Только чтение: в коде нет kill, удаления файлов или изменения сетевых правил.
- Терминальный интерфейс получает данные через Unix-сокет с правами `600` в каталоге `700`. Права файла и есть авторизация, поэтому подключиться может только root. Управляющие символы из имён процессов и командных строк в терминал не выводятся, так что имя процесса не может выполнить ESC-последовательность в вашем терминале.
- Веб-панель по умолчанию слушает только `127.0.0.1`. Сетевой адрес без пароля, `SSG_ALLOWED_HOSTS` и HTTPS не запустится.
- Без пароля панель доступна только пользователям из `SSG_LOCAL_UIDS` (по умолчанию root): владелец каждого подключения к loopback определяется по `/proc/net/tcp`, остальные получают 403. Иначе любой локальный пользователь мог бы читать то, что служба собирает от root: пути, открытые файлы и сокеты чужих процессов, результаты проверок.
- Проверка заголовка `Host` защищает от DNS rebinding, CSRF-токен защищает все POST-запросы, CSP запрещает inline-скрипты. Имена и командные строки процессов выводятся только как текст, поэтому злоумышленник не может внедрить HTML через имя своего процесса.
- Секреты в командных строках (`--password=…`, `-pПАРОЛЬ` у mysql, `user:pass@` в URL, `*_TOKEN=…`, ключи AWS и GitHub, JWT, токены ботов) маскируются **до** анализа, сохранения и вывода. Значения переменных окружения не читаются в историю вообще. В журнал не пишутся пароли, cookie и командные строки.
- Служба работает от root, потому что без этого нельзя увидеть процессы других пользователей, но с урезанными возможностями: `CAP_SYS_PTRACE` и `CAP_DAC_READ_SEARCH`. Файловая система для службы только на чтение, кроме `/var/lib/serversecuritygo`; включены `NoNewPrivileges`, фильтр системных вызовов, лимиты `MemoryMax=256M` и `CPUQuota=50%`.

### Журналы входов и расследование

Раздел **«Входы»** читает локальные события SSH, sudo/su, изменения учётных записей, wtmp/btmp/utmp и разреженный lastlog. SHA256-отпечатки SSH сопоставляются с `authorized_keys` пользователей. Неудачные попытки группируются по IP, пользователю и часу. Служба сохраняет виденные IP в `auth-state.json`; первый импорт создаёт исходную историю и не объявляет все адреса новыми. Срок хранения — меньшее из `SSG_AUTH_LOG_DAYS` и `SSG_HISTORY_RETENTION`. `SSG_AUTH_LOG_ENABLED=false` отключает сборщик.

Раздел **«Хронология»** и `/api/timeline?since=48h` объединяют историю процессов, входы и метаданные недавно изменённых файлов. `/api/logins` защищён общей авторизацией. ctime — время изменения inode, а не создания файла: его меняют также chmod/chown и обслуживание пакетов. Недавний ctime при старом mtime требует сопоставления с действиями администратора, но не доказывает подделку времени. Окна обновления пакетов приблизительны и не подавляют находки.

Метаданные файлов собирает отдельный обработчик раз в час: обход не задерживает сканирование процессов и heartbeat watchdog. До первого результата хронология показывает, что обход ещё выполняется.

```sh
serversecuritygo triage --format html --output /root/triage.html
serversecuritygo triage --full --format json --output /root/triage.json
serversecuritygo timeline --since 48h --format md --output /root/timeline.md
serversecuritygo recent --days 3 --format json --output /root/recent.json
serversecuritygo collect --output /var/backups/serversecuritygo/evidence.tar.gz
```

`triage` объединяет сканирование процессов, аудит настроек, входы, недавно изменённые файлы и десять приоритетных проверок с экранированными командами. `--full` дожидается обхода PID, проверки выбранных файлов dpkg и ограниченного инвентаря SUID/capabilities. Команды проверки только показываются. Доступны text/JSON/HTML/Markdown и прежние коды выхода `--fail-on`. При `SSG_HOST_ROOT`, указывающем на образ диска, и стандартном `/proc` команды расследования исключают живые процессы рабочей машины и явно отмечают недоступные проверки. Разовые команды не записывают историю службы и эталон входов.

`collect` создаёт новый архив без перезаписи, требует закрытый каталог назначения (700), выставляет архиву и его файлам права 600. Включает данные процессов, сети и аудита, ограниченные копии журналов и файлов закрепления, maps, **имена переменных окружения без каких-либо значений**, SHA256 исполняемых файлов и доступные копии удалённых/memfd-бинарников. `/proc/PID/exe` — единственное намеренное исключение для чтения симлинка; идентичность PID и метаданные файла проверяются повторно. `MANIFEST.sha256` содержит хеши сохранённых файлов, `collection.json` — сведения о пропусках. CLI также выводит SHA256 архива. Не запускайте собранные бинарники. Сбор доступен только через CLI; веб-команды сбора и скачивания архивов не включены.

Общий предел по умолчанию — 500 МиБ (`SSG_COLLECT_MAX_MB`), один бинарник — 50 МиБ (`SSG_COLLECT_MAX_BINARY_MB`), время — три минуты. Общий бюджет ограничивает сжатый архив, несжатые файлы и чтение бинарников; отдельные журналы и конфигурации ограничены 2 МиБ. Приватные ключи, shadow/gshadow и `.env` исключены, распознанные секреты в текстах маскируются. Архив всё равно содержит персональные данные и потенциально чувствительные команды: храните его закрытым. Манифест подтверждает согласованность сохранённых байтов, но не подлинность хоста и не атомарность снимка файловой системы.

Разбор входов ограничен байтами и числом записей: до 5 000 событий и ключей, фиксированные ротации auth.log (`.1`, `.2.gz`). Недоступные источники и превышения лимитов обозначаются как неполнота. Поддерживаются little-endian форматы glibc amd64 и arm64; неизвестная архитектура образа не угадывается. Бинарный journald остаётся следующим этапом: без auth.log видимость аутентификации ограничена. Нельзя достоверно восстановить опции ключей/нестандартный `AuthorizedKeysFile`, причину очистки journal и все схемы ротации. Уменьшение journal и подавление истории оболочки требуют проверки; пустые журналы сами по себе не доказывают удаление. Обход файлов ограничен 100 000 путей, 10 000 результатов и десятью секундами; симлинки не обходятся. Служба обновляет метаданные раз в час; хронология содержит только доступные сохранённые наблюдения.

Новые ID: `login_new_ip`, `login_password_root`, `login_after_bruteforce`, `login_unusual_time`, `login_service_account`, `log_wtmp_truncated`, `log_wtmp_gap`, `log_authlog_truncated`, `log_history_null`, `log_journal_vacuum`, `log_utmp_missing`. Аутентификация служебной учётной записи имеет LOW без подтверждённого терминала и HIGH при сопоставленном TTY сессии. Отмечается успешный вход после не менее десяти ошибок с того же IP за десять минут; учитывайте общий NAT и работу администратора. После компрометации ядра локальные проверки не восстанавливают доверие: сохраните образ диска и исследуйте его независимо.

Форматы сверены 16.11.2026 с [определениями utmp glibc](https://github.com/bminor/glibc/blob/master/bits/utmp.h) и [ABI aarch64](https://github.com/bminor/glibc/blob/master/sysdeps/aarch64/bits/wordsize.h). Linux CI сопоставляет созданную на C запись с Go-парсером и сохраняет удалённый бинарник отдельного тестового процесса.

### Карточки находок, расширенный аудит и снимки

Карточки процессов, системных находок и аудита показывают объяснение, возможные штатные причины, команды проверки, рекомендации, контекст ATT&CK и до восьми связанных событий из последних 2000 записей истории. События процесса связаны по PID и времени старта, файла — по пути. ATT&CK и принадлежность файла пакету не доказывают атаку или целостность. Команды приложение не выполняет.

Аудит охватывает защитные параметры ядра, временные монтирования и чувствительные права, SUID/SGID и capabilities файлов, необходимость перезагрузки, более новое установленное ядро того же варианта, давность данных APT, unattended-upgrades, сроки поддержки ОС и сохранённую конфигурацию firewall. `audit --full` ждёт инвентаризации файлов; быстрый аудит помечает эти проверки как неполные. «Нет данных» также означает неподдерживаемый синтаксис или отсутствующий источник. Действующие правила ядра и firewall провайдера не проверяются. Подсчёт ожидающих security-обновлений и чтение правил через netlink остаются следующим этапом.

Отдельный обработчик обходит файлы каждые шесть часов со скоростью 2000 путей/с. Настройки: `SSG_FS_SCAN_INTERVAL`, `SSG_FS_SCAN_RATE`, списки через запятую `SSG_FS_SCAN_EXCLUDE` и `SSG_FS_SCAN_MOUNTS` для дополнительных точек монтирования. По умолчанию проверяются корневая ФС и `/dev/shm`, без перехода на другие ФС и по симлинкам. Исключены `/proc`, `/sys`, `/dev` вне `/dev/shm`, `/run`, хранилища Docker/контейнеров, сетевые и FUSE-монтирования. Пределы: 2 млн путей, 10 000 привилегированных файлов/находок, глубина 128 и 30 минут. Достижение пределов, отмена и ошибки чтения явно означают неполную проверку. Первый полный инвентарь сохраняется в `baseline.json`; новые привилегии дают `fs_privilege_new`. Принадлежность пакету не является доверенной подписью. Новые ID: `fs_suid_inventory`, `fs_capabilities`, `fs_world_writable_system`, `fs_unowned`, `fs_privilege_new`, `fs_inventory_pending`, `fs_inventory_unavailable`, `new_public_listener`, `ports_baseline_unavailable`.

```sh
serversecuritygo audit --full --format json --output /root/audit.json
serversecuritygo baseline save --name before-upgrade
serversecuritygo baseline list
serversecuritygo diff --from before-upgrade --to now --format json --output /root/diff.json
serversecuritygo baseline accept --ports
```

Снимки хранятся в `SSG_DATA_DIR/baselines`: каталог 700, файлы 600. Именованные снимки не перезаписываются. Сохранение и сравнение с `now` ждут ограниченного обхода ФС. В снимке — локальные пользователи/группы, публичные порты и бинарники владельцев, сохранённые юниты/службы systemd, SUID/SGID, capabilities, отпечатки ключей из стандартных authorized_keys, имена модулей, хеши выбранных критичных бинарников и статусы аудита. Хеши паролей, ключевой материал, комментарии ключей и содержимое юнитов не сохраняются. Для сравнения нужен одинаковый machine-id; сравниваются только полные разделы с одинаковой областью проверки. Недоступные данные не превращаются в сообщения об удалении. Снимок собирается за некоторый промежуток времени и не доказывает подлинность хоста.

Установка создаёт `installation`; после обновления служба создаёт его при первом доступном инвентаре, если снимка ещё нет. Еженедельные снимки сохраняются автоматически, остаются последние 12; ручные снимки не удаляются. Веб/TUI «Изменения» и `/api/changes` обновляются раз в час по последнему инвентарю ФС, который обычно может отставать до шести часов. Для окна семи дней выбирается последний доступный снимок до его начала; точные даты показаны в интерфейсе. Пока истории недостаточно, выводится отсутствие данных.

Полный исходный список публичных портов задаёт ожидаемые сочетания протокола, адреса, порта и бинарника. Новое сочетание даёт HIGH `new_public_listener` и событие `listen`. После проверки `baseline accept --ports` заменяет только этот эталон; нужны полные таблицы сокетов и известные бинарники владельцев. Служба подхватывает принятие в течение минуты. Неизвестные владельцы, в том числе публикации Docker без видимого бинарника, запрещают принятие. Firewall и остальные находки не изменяются.

Офлайн-таблица поддержки сверена 18.11.2026 по [Ubuntu](https://ubuntu.com/project/docs/release-team/list-of-releases/) и [Debian](https://www.debian.org/releases/): обычная поддержка Ubuntu и LTS Debian отделены от Pro/ESM/ELTS, действующее покрытие которых проверяет администратор. Capabilities читаются по [формату Linux](https://github.com/torvalds/linux/blob/master/include/uapi/linux/capability.h), ревизии 1–3.

### Проверка allowlist, обучение и дополнительные детекторы

В карточках процессов действие **Это легитимно** предлагает JSON-фрагмент для конкретного исполняемого файла, пользователя и ID признака. Поле `"exact": true` не даёт символам `*`, `?` и `[` в имени файла превратиться в шаблон allowlist. Проверьте фрагмент и самостоятельно добавьте правило в существующий список: копирование ничего не меняет. Для процессов CRITICAL, сильных, справочных и уже подавленных признаков предложения не создаются. Для системных находок и аудита автоматического действия allowlist нет.

По умолчанию обучение выключено: `SSG_LEARNING_HOURS=0`. Значение 1–168 включает сбор кандидатов на проверку. Нужны минимум три наблюдения за пять минут, риск процесса не выше LOW и слабый признак с весом не более 10. В текущем скане признак должен оставаться подходящим; рост до HIGH/CRITICAL или сильный сигнал удаляет кандидата. Первое окно обучения и счётчики сохраняются в `learning.json` между перезапусками; изменение настройки не начинает окно заново. Обучение не снижает оценку, не принимает базовую линию и не редактирует allowlist. После проверки кандидатов панель также предлагает текст команды `baseline save`, чтобы сохранить именованный снимок всей текущей системы; команда не принимает порты и не подавляет признаки. Раздел **Обучение**, `/api/learning` и TUI показывают кандидатов и предупреждения о широких правилах. Если правило 30 календарных дней не совпадало с наблюдаемой находкой, предлагается проверить его необходимость; простой службы тоже учитывается, поэтому это не доказательство устаревания правила. Пределы состояния — 1000 кандидатов и 1000 записей использования правил; повреждённое состояние сохраняется с предупреждением.

Новые признаки: `bpf_unexpected`, `raw_packet_socket`, `iface_promisc`, `exe_packed`, `exe_static_in_temp` и опциональный `webshell_pattern`. eBPF проверяется по видимым дескрипторам процессов и `fdinfo`: это не полный перечень программ ядра и не подтверждение их прикрепления. Таблицы AF_PACKET связываются с владельцами видимых дескрипторов; приложение не захватывает пакеты. Известные пакетные инструменты с исполняемым файлом root без права записи для группы и остальных получают меньшую оценку, однако принадлежность пакету не доказывает целостность. Режим promiscuous бывает штатным для мостов и виртуализации. Сохраняется оценка по независимым категориям: одна сильная категория сама по себе не поднимает процесс до HIGH.

Проверка ELF работает отдельно при старте и раз в час: максимум 256 разных исполняемых файлов, 32 МиБ на файл, 64 МиБ суммарно и минутный бюджет работы. Кеш применяется только при совпадении поколения процесса, пути, устройства/inode, ctime, размера и mtime; срок — два часа. Новые и изменившиеся процессы до проверки явно отмечаются как неполные данные. Маркеры UPX требуют сверки происхождения файла; одна высокая энтропия даёт INFO. Файлы не запускаются и не распаковываются. Для eBPF установлены пределы 128 дескрипторов на процесс и 2048 на скан; для AF_PACKET — 128 пространств имён и 10 000 строк на скан. Пропуски обозначаются ID `advanced_pending`, `advanced_process_pending`, `advanced_unavailable`, `packet_inventory_unavailable`, `promisc_unavailable`.

Поиск веб-шеллов по умолчанию выключен: `SSG_WEBSHELL_ENABLED=false`. При включении обработчик работает, только если наблюдается nginx, Apache/httpd или PHP-FPM. Он читает статические пути `root`/`DocumentRoot` из локальных конфигураций и `/var/www`, затем проверяет `.php`, `.jsp`, `.aspx`, изменённые за `SSG_WEBSHELL_DAYS` дней: по умолчанию 7, диапазон 1–365. Пределы: 32 корня, 100 000 путей, 1 МиБ на файл содержимого, 16 МиБ содержимого суммарно и 1000 находок; поиск конфигурации ограничен 256 файлами по 256 КиБ. Симлинки не обходятся; пути с переменными не поддерживаются и делают результат неполным. Пути внутри контейнеров могут быть невидимы. В находку попадают ID шаблонов, а не исходный код или извлечённые секреты. Совпадения INFO/MEDIUM требуют проверки и встречаются в легитимном административном коде. Связь с `web_spawns_shell` даёт контекст, но не доказывает, что именно этот файл вызвал запуск.

### SARIF и диагностика установки

```sh
serversecuritygo scan --full --format sarif --output /root/scan.sarif --min-risk INFO
serversecuritygo audit --full --format sarif --output /root/audit.sarif
serversecuritygo triage --full --format sarif --output /root/triage.sarif
serversecuritygo explain exe_memfd
serversecuritygo explain kern_aslr --format json
serversecuritygo doctor --format json --output /root/doctor.json
```

SARIF 2.1.0 — локальный экспорт для `scan`, `audit` и `triage`: ID правил, уровни, экранированные URI файлов, ATT&CK в `properties.attack`, явное подавление allowlist и признак неполного запуска. Успешные, справочные, неизвестные и неприменимые результаты аудита различаются. Действуют прежние коды выхода и фильтры риска. Приложение не отправляет отчёты и не подключается к интеграциям. Файлы отчётов имеют права 600.

`explain` читает встроенный каталог признаков и проверок без сканирования хоста. Параметры `{N}` в справочном тексте заполняются значениями конкретной находки. `doctor` читает пути и права установки, основной файл юнита systemd, выборку до 32 чужих процессов, доступность auth.log, версию ядра и метаданные dpkg. Он не выполняет команды и не меняет права. Проверка не доказывает готовность службы, правильность загруженного юнита и drop-in, доступ ко всем PID или наличие исправлений CVE; необходимые дальнейшие действия указаны в рекомендациях. При проверке образа через `SSG_HOST_ROOT` стандартный `/proc` рабочей машины не подмешивается. Поиск процессов в вебе и TUI учитывает ID признаков, пользователей, контейнеры, локальные и удалённые порты.

### Группы файловых находок

В разделе «Система» повторяющиеся `fs_unowned` сворачиваются в группы по каталогу и UID/GID. Этот признак означает, что UID или GID не найден в локальных `/etc/passwd` и `/etc/group`; он не описывает принадлежность пакету и сам по себе не доказывает заражение. Каталог группы ограничен первыми тремя компонентами родительского пути: например, `/usr/local/include/node/a.h` относится к `/usr/local/include`. Разные уровни риска и состояния подавления не объединяются. Одиночные записи, неизвестный формат доказательств и другие типы находок остаются отдельными строками.

В вебе нажмите название группы, чтобы открыть исходные находки; кнопка над таблицей возвращает к группам. В TUI Enter открывает список файлов, ещё один Enter — подробности выбранного файла; ← или Esc из списка файлов возвращает к группам. Поиск `/` проверяет каждый исходный путь, ID признака, уровень риска и доказательства, включая UID/GID. `y` копирует каталог группы или путь выбранного файла, `Y` — JSON находок группы или одной находки; объём буфера обмена зависит от терминала. Обновление данных сохраняет открытую группу, пока она существует.

Группировка меняет только представление: исходные находки, история, оценки риска и CLI-отчёты сохраняются. В `GET /api/system` массив `findings` остаётся полным; дополнительный массив `groups` содержит `key` (непрозрачный ключ), `directory`, `owner` и `indices` — индексы с нуля в `findings` того же ответа. TUI строит группы и при подключении к старой службе; веб при отсутствии `groups` показывает обычный список.
